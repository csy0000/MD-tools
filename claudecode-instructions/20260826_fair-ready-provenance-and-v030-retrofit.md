# FAIR-ready simulation records and non-destructive 0.3.x retrofit

Work on the current `dev` branch of `csy0000/MD-templates`.

Start from the current `dev` head. At the time this instruction was written it was
`1489b4c6625de19a5c0514c05b1e1e158fd67d94` (`0.3.1`). If `dev` has advanced, inspect the
intervening commits and preserve applicable user work.

This task makes data produced by MD-templates **FAIR-ready / FAIR-aligned**. Do not claim that a
simulation directory is itself a FAIR dataset: permanent dataset identity, storage, access policy,
the final archive checksum manifest and lifecycle belong to `MD-data`.

Preserve the simplified six-command public architecture:

- `md-template init`
- `md-template install`
- `md-openmm show-default`
- `md-openmm sys-config`
- `md-openmm sys-gen`
- `md-openmm md-gen`

Do not add a seventh public command, restore a workflow engine, add a registry, or reintroduce the
deleted bundle/schema framework. Keep `generate_system()` in
`src/md_templates/openmm/sysgen.py` and `generate_md()` in
`src/md_templates/openmm/mdgen.py`. Do not restore root-level `MD_system_gen.py` or
`MD_input_gen.py`.

Because this adds a new persistent output contract after release 0.3.1, set the development version
to `0.4.0.dev0`. Do not merge into `main` and do not create, delete or move a release tag.

## 1. Cross-repository ownership

Document and enforce this boundary:

| repository | responsibility |
|---|---|
| `MD-templates` | system construction, force-field record, resolved simulation protocol, seeds, generated scripts and execution provenance |
| `MD-data` | permanent dataset ID, immutable storage under `$MD_DATA`, complete archive checksums, searchable metadata, locations, retention, replacement and access lifecycle |
| `MD-analysis` | analysis configuration, software identity, consumed dataset IDs/checksums and derived-result lineage |
| future project-template / project repository | project-specific inputs/configs/workflows and exact locks for the three components and registered datasets |

Update `README.md` and `CLAUDE.md` to state this relationship, with links to:

- https://github.com/csy0000/MD-templates
- https://github.com/csy0000/MD-data
- https://github.com/csy0000/MD-analysis
- the future project-template repository, explicitly marked not yet available.

The current `CLAUDE.md` contains durable rules from the retired, overengineered run-management
architecture. Replace those stale requirements with concise rules for the current six-command
architecture, scientific safety, generated-project portability, FAIR provenance, tests and the
cross-repository boundary. Do not instruct future agents to rebuild registries, schema-migration
engines, committed-chunk databases or workflow managers.

Add `docs/FAIR_HANDOFF.md` explaining:

- Findability and accessibility are completed by MD-data registration, not by MD-templates alone;
- interoperability comes from documented YAML/JSON records, explicit units and relative paths;
- reusability comes from original inputs, resolved configs, exact implementation identity,
  force-field construction, seeds, commands, environment and lineage;
- unknown historical facts remain `unknown`; they are never guessed.

## 2. Forward system-generation output

A new `md-openmm sys-gen` output must be self-contained enough to rebuild or reuse the prepared
system without the original project checkout.

The generated tree must include:

```text
inputs/
├── original_inputs/
│   └── <exact original input basename>
├── preparation/                 # only scientifically relevant construction artifacts, when any
├── system.xml
├── topology.pdb
├── solute.pdb
├── initial_state.xml
├── solute.yaml
├── forcefield.json
├── resolved_sys.config.yaml
├── provenance.yaml
├── SHA256SUMS
└── sys-gen.log
```

Requirements:

1. Copy the original PDB, MOL or SMI file byte-for-byte into `original_inputs/`.
2. Preserve its basename and checksum. Reject a collision rather than silently renaming or
   overwriting it.
3. Preserve only scientifically relevant construction artifacts already generated by the builder:
   - for the ParmEd/tleap implicit path, retain applicable `tleap.in`, `tleap.log`, prmtop,
     rst7/inpcrd, mol2/frcmod or charged ligand representation when they exist;
   - for the OpenFF route, retain the prepared ligand representation carrying the bond orders,
     protonation and final partial charges when it exists;
   - do not copy caches, environments, temporary solvent files or the complete `_work/` tree.
4. Every required path in the records must be relative to `inputs/`. Absolute paths may be
   recorded only as optional execution observations and must never be needed to reuse the bundle.
5. Relocating `inputs/` must not invalidate its internal references.

### forcefield.json

Write one authoritative, human-readable and machine-readable force-field construction record. It
must contain the applicable values, with explicit `null` where a concept does not apply:

- record format identifier and version;
- peptide/ligand route;
- protein force field and exact OpenMM XML/resource name;
- ligand force field name/version and charge method;
- prepared ligand artifact and its checksum when applicable;
- water model and exact XML/resource name;
- explicit solvent box shape, padding, ions, ionic strength and cutoff;
- implicit solvent model and radius set;
- nonbonded method and applicable PME/cutoff settings;
- constraints, rigid-water choice, hydrogen mass and HMR scope;
- builder route used to construct the final OpenMM System;
- relevant package versions;
- checksums of retained force-field/parameterization artifacts.

Do not parse the prose of `tleap.log` to guess values already known by the builder. Record the
actual selected values at the point where the System is constructed.

### System provenance

Extend `inputs/provenance.yaml` without creating a parallel provenance framework. Give it one
format identifier such as `md-templates-system-provenance/v1` and record:

- creation time in UTC;
- exact command as an argument list, not a shell string;
- MD-templates package version;
- Git commit and dirty state when a checkout is available;
- an installed-package fingerprint that is non-null even when Git metadata is unavailable;
- PEP 610 `direct_url.json` information when present;
- Python and OpenMM versions;
- relevant preparation-package versions when available;
- original-input relative path and SHA-256;
- resolved system-config hash;
- `forcefield.json` hash;
- topology atom count, OpenMM particle count, solute atom count, periodicity and box vectors;
- relative paths to all scientific payload files;
- the checksum-manifest path.

The installed-package fingerprint must be deterministic: hash the sorted relative paths and
contents of the installed `md_templates` Python/template resource files, excluding bytecode,
caches and mutable metadata. This identifies a locally built or installed implementation even when
`git_commit` is null. Do not add a custom build backend solely to stamp a commit.

Write `inputs/SHA256SUMS` last. It must hash every regular file under `inputs/` except
`SHA256SUMS` itself and transient files. Use relative POSIX paths, deterministic sorting and
streaming reads. A fresh validation must reproduce every digest.

## 3. Forward MD-generation provenance

Keep the existing directory tree and independent stage scripts. Add FAIR provenance without
changing the scientific protocol:

```text
MD/
├── md.config.yaml
├── provenance.yaml
├── generated-files.sha256
├── minimization/
├── eq/
├── cMD/
└── REST2/
```

Extend `MD/provenance.yaml` with a format identifier such as
`md-templates-md-provenance/v1` and record:

- generation time and exact `md-gen` argument list;
- the same implementation identity fields used by sys-gen;
- relative path to `inputs/`;
- SHA-256 of `inputs/provenance.yaml`, `inputs/forcefield.json` and
  `inputs/SHA256SUMS`;
- resolved system-config and MD-config hashes;
- selected methods and the exact common-stage plan;
- base random seed and all generated stage/replica seeds;
- relative paths to generated scripts/configurations;
- checksum-manifest path.

Write `MD/generated-files.sha256` for files produced by `md-gen` before dynamics begins. Its
scope must be explicit: it identifies generated configuration and executable inputs, not later
trajectories or checkpoints. Do not call it the final dataset checksum manifest.

Moving sibling `inputs/` and `MD/` together must remain sufficient. Generated scripts must not
import `md_templates`, name the source checkout or require network access.

## 4. Runtime records

Do not add a run database or committed-chunk framework. Use the existing runtime files and add only
the missing concise records.

### Common stages

Keep `stage.yaml` and `resolved_stage.yaml`. Extend the resolved record with:

- record format/version;
- started and finished UTC;
- status (`completed` only after successful final-state creation);
- implementation fingerprint/version/commit already carried into the generated project;
- input-state relative path and checksum;
- stage configuration SHA-256;
- platform and selected CUDA device;
- configured and completed steps/iterations;
- seeds, restraint and barostat state;
- output filenames, byte sizes and final-state/checkpoint SHA-256.

Do not hash a downstream stage's parent checkpoint. The normal handoff remains the parent's
`final_state.xml`.

### cMD

Write a concise `cMD/resolved_run.yaml` after each successful invocation and append one JSON
object per invocation to `cMD/invocations.jsonl`. Record:

- invocation index and start/finish UTC;
- starting and ending step/time;
- configured target duration and work performed in this invocation;
- command arguments;
- input final-state or own checkpoint used;
- platform/device and seeds;
- trajectory filenames, atom scopes, frame counts and byte sizes;
- final-state/checkpoint checksums;
- status.

Continuation must append; it must not erase the earlier invocation history or duplicate a JSONL
entry.

### REST2

Keep the existing per-tau equilibration records and `exchange_attempts.csv`. Add:

- a root `REST2/resolved_run.yaml`;
- append-only `REST2/invocations.jsonl`;
- for every replica, the recorded tau, derived scaling factors, seeds, device, start/end step,
  checkpoint/final-state checksums, trajectory frame counts and sizes;
- invocation and lifetime exchange-attempt ranges and counts;
- starting/restored exchange phase and RNG provenance;
- confirmation that positions and box vectors are exchanged together;
- common physical temperature/pressure and Hamiltonian scaling description.

Do not change REST2 scaling, exchange acceptance, duration accounting, GPU scheduling, trajectory
content, box swaps, seeds or extension behavior in this task.

Do not compute trajectory SHA-256 during every simulation invocation. Record paths, sizes and frame
counts at runtime; MD-data computes the final complete trajectory checksums once during archival.

A failed or interrupted invocation must never be labelled completed. If a final resolved record is
not safely writable, leave the existing logs/checkpoints and fail nonzero rather than inventing a
successful status.

## 5. Non-destructive retrofit for MD-templates 0.3.x data

Add a repository script, not a new installed public command:

```bash
python scripts/retrofit_fair_v030.py \
  --inputs /path/to/inputs \
  --md /path/to/MD \
  --output /path/to/fair-registration \
  [--original-input /path/to/original.pdb] \
  [--environment /path/to/environment-record]
```

The script must require Python plus PyYAML only. It must not require OpenMM, CUDA, network access or
the source checkout.

Safety rules:

1. Treat `inputs/` and `MD/` as read-only. Never change a timestamp, rename a file, regenerate a
   state, rewrite a trajectory, or add a file inside them.
2. Refuse a non-empty output directory.
3. Stream hashes and show progress for large files.
4. Use relative paths in every generated record.
5. Exclude the output sidecar from the source-tree inventory when it is under the common project
   root.
6. Do not infer scientific values from directory or file names.
7. For every retrospective value record an evidence status:
   - `recorded`: directly present in a 0.3.x config/provenance/runtime record;
   - `derived`: deterministic calculation from recorded content;
   - `user_supplied`: supplied explicitly to the retrofit command;
   - `unknown`: evidence is unavailable.
8. Never use `inferred` as a scientific evidence status.
9. An optional original input is accepted only when its SHA-256 matches the hash recorded by the
   0.3.x `inputs/provenance.yaml`. A mismatch is a hard failure.
10. A suggested replay command may be written as `reconstructed_command`; never label it as the
    original command unless the original command was recorded.

Write:

```text
fair-registration/
├── system-record.yaml
├── run-record.yaml
├── forcefield.json
├── file-inventory.yaml
├── SHA256SUMS
├── validation.json
└── README.md
```

The final sidecar checksum manifest must cover every retained file under `inputs/` and `MD/`,
using paths relative to their common project root, plus the non-circular sidecar payload files.
Document exactly which manifest files are excluded to avoid self-hashing.

Classify the retrospective closure:

- **A — rebuildable**: original molecular input is present and checksum-matched; resolved system and
  MD configs, prepared system, exact implementation identity and required run records exist.
- **B — prepared-system reproducible**: the prepared OpenMM System/topology/state and protocol are
  sufficient to rerun or continue the simulation, but the original molecular input, exact build
  environment or exact code identity is incomplete, so parameterization cannot be reproduced
  completely.
- **C — archival/analysis only**: outputs can be preserved and analyzed, but the prepared simulation
  cannot be reproduced reliably.

The grade and every reason lowering it must be machine-readable. Do not upgrade a grade based on a
human-readable filename or an undocumented assumption.

The retrofit output is a registration candidate only. It must not assign an MD-data dataset ID,
move data into `$MD_DATA`, claim immutability, delete the source, or modify the 0.3.0/0.3.1 tags.
Those actions belong to MD-data registration.

## 6. Tests

Keep the suite focused.

### Metadata/unit tests without MD

Test:

- deterministic installed-package fingerprints;
- Git-present and Git-absent provenance;
- original input copying and collision refusal;
- `forcefield.json` for explicit OPC and implicit GBn2/mbondi3;
- deterministic checksum ordering and mutation detection;
- no absolute required paths;
- relocation of an `inputs/` + `MD/` pair;
- generated-project operation without importing `md_templates`;
- wheel contents include every new helper/resource needed by public generation;
- legacy retrofit leaves every source file hash and timestamp unchanged;
- correct A/B/C classification;
- optional original-input checksum acceptance and mismatch refusal;
- recorded/derived/user_supplied/unknown evidence labels;
- output-directory refusal;
- absence of dataset IDs and storage actions.

Use a small fixed synthetic 0.3.x fixture for the retrofit tests. Do not make tests depend on
private workstation data or `$MD_DATA`.

### Targeted CUDA smoke tests

Run only the small GPU workflows needed to prove runtime-record production:

- one explicit cMD common chain and production invocation;
- one tiny explicit REST2 per-tau equilibration and exchange-production invocation;
- one continuation/extension proving invocation history appends and lifetime indices remain
  monotonic;
- one implicit run proving the provenance says GBn2/mbondi3 and contains no pressure/barostat.

All tests that minimize or integrate a molecular system must use CUDA. Do not substitute CPU or
Reference. Do not repeat nanosecond-scale validation and do not rerun unrelated expensive tests
during development.

Before completion, run the relevant non-MD suite and these targeted CUDA tests. A complete
pre-release suite remains a later release action.

## 7. Compatibility and non-goals

This task must not:

- change any force-field, solvent, box, cutoff, salt, restraint, integrator, timestep, ensemble,
  REST2 ladder, scaling, exchange or output-interval default;
- alter scientific coordinates, velocities, checkpoints or trajectory contents;
- change the nested `MD/eq/` layout;
- add project-specific systems, conclusions, paths or private data;
- require an MD-data checkout at generation/runtime;
- upload, move, delete or register data;
- mint a DOI or dataset identifier;
- add a registry, database, workflow engine, schema-migration framework or automated archive
  lifecycle;
- modify or move existing release tags.

Existing 0.3.x output remains valid. The new forward provenance format is additive. The retrofit
script interprets legacy output without rewriting it.
