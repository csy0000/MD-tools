OpenMM Explicit-Water Template: First Refactor Instructions

Mission

Refactor this repository into a generic, reusable base for conventional molecular dynamics (MD)
and omega-selective REST2 simulations in explicit water with OpenMM.

Complete the seven requirements below before adding new simulation methods or features. Treat
scientific correctness, restart continuity, reproducibility, and clear provenance as hard
requirements. Do not preserve obsolete names or compatibility shims that conflict with this
mission.

The target public naming is:

Python distribution: md-templates

Python import package: md_templates

OpenMM command-line program: md-openmm

Do not use the old project names in compatibility aliases, comments, examples, artifacts, package
metadata, or documentation.

General working rules

Inspect the current repository, tests, manifests, reports, and active CLI before editing.

Preserve only the explicit-water conventional-MD and REST2 functionality needed by the new
generic template.

Make changes in small, reviewable commits if committing is requested. Do not publish, push, or
open a pull request unless explicitly asked.

Do not silently migrate scientific settings. Reject ambiguous or incompatible old inputs with a
precise error, or provide a deterministic one-time migration command.

Every scientific choice must be represented in the resolved configuration and run manifest.

Add regression tests before or alongside each fix. A passing smoke test is not evidence of
scientific convergence; keep those concepts separate in documentation.

Do not claim completion until the full test suite and the explicit acceptance checks at the end
of this file pass.

1. Run-directory and continuation contract

Replace the current always-new, immutable, timestamped run behavior with an explicit fresh-run and
resume contract.

Public interface

Support these concepts consistently for conventional MD and REST2:

--out-root ROOT: parent directory for runs.

--run-name NAME: optional user-selected directory name for a fresh run.

--resume-run RUN_DIR: resume an existing continuous simulation in that exact directory.

Rules:

If --run-name is supplied for a fresh run, create exactly ROOT/NAME. Do not add a timestamp,
system name, method name, or hash to it.

If --run-name is omitted, generate a collision-resistant timestamped default name that also
contains a short system/method identifier where useful.

A fresh run must refuse to overwrite an existing directory.

A resume must write into the existing run directory. It must not create a sibling directory.

--run-name and --resume-run are mutually exclusive.

Do not guess that two simulations are continuous. A resume is allowed only after continuity
validation succeeds.

If continuity validation fails, stop before writing simulation output and explain which settings
differ. Tell the user to start a fresh run; do not silently create one.

Continuity validation

Store a continuation contract in the run manifest and validate it before loading any state. At
minimum, require equality of:

prepared-system fingerprint and particle count;

topology identity and atom ordering;

force fields, charges, water model, ions, box preparation, constraints, HMR, nonbonded method,
cutoff, switching, dispersion correction, PME tolerance, and REST2 omega-exclusion behavior;

method (md versus rest2), scale-factor ladder, exchange interval, timestep, temperature,
friction, ensemble, precision, integrator kind, random-seed plan, and chunk length;

OpenMM version and exact checkpoint compatibility metadata when an exact checkpoint is used.

The target number of chunks may be increased when extending the same simulation, provided every
other continuation-defining setting is unchanged and the new target is not less than the completed
prefix. Record the original target, each extension, and the final target in the run manifest or an
append-only continuation history.

Restart artifacts and crash consistency

Save an OpenMM checkpoint and a portable serialized State at the end of every completed chunk.

Write completion metadata only after the end checkpoint and State are safely written.

Use temporary files followed by atomic replacement for checkpoint, State, and done.json files.

Resume from the last contiguous completed chunk. Reject gaps or conflicting completion markers.

Prefer the checkpoint for exact continuation only when compatibility checks pass.

If a checkpoint is incompatible but the portable State is valid, require an explicit user choice
such as --resume-from-state because this is distributionally continuous but not bitwise
identical. Record that event prominently in provenance.

Remove or deterministically replace partial files from an incomplete chunk before rerunning it;
never append to a partial trajectory without validating its last frame and step.

Preserve absolute simulation step and time across continuation.

Add end-to-end tests covering fresh named runs, default timestamped runs, successful continuation,
extension by more chunks, incompatible continuation, missing checkpoint with State fallback, a gap
in completed chunks, and a crash after one replica writes its checkpoint but before all replicas
complete the REST2 chunk.

2. Make chunk count an input, never an inferred rounded value

The user must specify both the number of chunks and the length of each chunk. Remove total duration
as an independent input from the active schema and CLI.

Use these canonical fields:

Conventional MD: production.md.n_chunks and production.md.chunk_ns

REST2: production.rest2.n_chunks and production.rest2.chunk_ns

If the external manifest keeps a shorter rest2 block, map its n_chunks and chunk_ns to the
canonical resolved configuration without creating a second source of truth.

Requirements:

n_chunks must be an integer greater than zero. Reject booleans, floats, zero, and negatives.

chunk_ns must be finite and positive.

Derive total_ns = n_chunks * chunk_ns for conventional MD.

Derive total_ns_per_replica = n_chunks * chunk_ns for REST2.

Store the derived totals in resolved configuration, status, summaries, and manifests, but never
use them to reconstruct or round n_chunks.

Validate that a chunk is an exact integer number of integration steps.

For REST2, validate that a chunk is an exact integer number of exchange intervals.

Validate every reporter interval against the chunk length and timestep.

Remove every calculation of the form round(total/chunk), including legacy paths.

Bump the manifest schema version because this is a breaking change. Update shipped manifests,
examples, documentation, generated defaults, fingerprints, and tests together.

Reject schema-v1 experiment manifests with an actionable migration message, or implement and
test a deterministic migrate-manifest command. Do not silently reinterpret them.

3. Correct statistics across resumed REST2 runs

REST2 summaries must describe the whole run, not only the process invocation that finished it.

Treat the exchange log as the durable source of truth.

On resume, reconstruct attempted exchanges, accepted exchanges, pair-resolved counts,
pair-resolved acceptance, walker occupancy, phase parity, completed rounds, and current walker
mapping from the validated log up to the last completed chunk boundary.

Truncate log rows beyond the last completed chunk boundary only after saving an audit record of
what was removed and why.

Continue the exchange phase and RNG plan deterministically from persistent state. Do not merely
reseed based on the invocation count.

At finalization, compute all aggregate statistics from the complete exchange log, including data
from before continuation.

Report both lifetime totals and optional per-invocation deltas, clearly labeled.

Make summary regeneration idempotent: deleting only the summary and rebuilding it from durable
logs must produce the same scientific statistics.

Add a regression test comparing an uninterrupted deterministic CPU run with the same run split
across a stop/resume boundary. Validate step/time continuity, exchange phase, row count, lifetime
attempt/accept counts, pair statistics, and walker mapping.

4. Write the equilibrated structure with the selected NPT box

The selected NPT handoff State contains coordinates, velocities, and box vectors from one sampled
state. The human-readable equilibrated structure must contain the same periodic cell.

Before writing the equilibrated PDB, set the output topology's periodic box vectors from
final_state.getPeriodicBoxVectors() (or write through an equivalent path that explicitly uses
those vectors).

Do not mutate a shared topology object in a way that changes unrelated artifacts; copy it when
needed.

Preserve the serialized State as the authoritative production input.

Record the selected box vectors and volume in the equilibration summary.

Add a regression test that parses the written PDB CRYST1 record/topology, compares its vectors
and volume with the serialized selected State, and fails if the pre-NPT box was written.

Test both cubic and triclinic/rhombic-dodecahedral boxes with tolerances appropriate to PDB field
precision. If PDB precision is insufficient for a required comparison, also write PDBx/mmCIF and
document which structure file is authoritative.

5. Correct salt and ionic-strength provenance

Do not infer salt concentration from the minimum of whatever ion counts happen to exist.
Neutralizing counterions are not salt pairs.

For the currently supported monovalent NaCl-style setup:

Resolve and record the actual positive- and negative-ion residue names used by OpenMM.

Count each species separately, treating a missing species as zero.

Calculate added salt pairs as min(n_positive, n_negative).

Attribute excess ions to charge neutralization and verify that their signed charge balances the
declared solute formal charge.

Report requested salt molarity, realized salt-pair molarity, neutralizing-ion counts, total ion
counts, number of waters, and box volume as separate fields.

Name fields precisely. Do not call neutralizing counterions “ionic strength.”

If general multivalent ions are supported, compute ionic strength as
I = 0.5 * sum(c_i * z_i**2) using explicit valences. Otherwise reject unsupported ions rather
than applying the monovalent formula.

Add tests for neutral, +1, -1, and multicharged solutes at zero requested salt and at nonzero
requested salt. Include small-box cases where requested salt rounds to zero pairs. Verify that
counterion-only systems report zero realized salt-pair molarity.

Rename the Python distribution to md-templates.

Rewrite package descriptions, entry points, examples, environment names, wheel names, manifests,

Delete unrelated functionality

Trace imports and runtime use before deletion.

7. Omega-selective REST2 is the default implementation branch

Ordinary amide omega torsions must be excluded from REST2 torsion scaling by default. This is an
implementation choice, not a claim of a new enhanced-sampling method.

Configuration and CLI

Define one canonical boolean setting, rest2.omega_exclusion, defaulting to true.

Support the exact CLI form --omega-exclusion true|false for REST2 commands.

Optionally also support --no-omega-exclusion, but it must map to the same canonical setting.

CLI overrides must be written into the resolved configuration and run manifest.

Changing this setting changes the scientific Hamiltonian and must be included in configuration
hashes, continuation checks, and provenance. A run cannot be resumed after toggling it.

Behavior

When enabled, classify ordinary amide omega bonds and proline-like exceptions using the existing
auditable chemistry-aware logic. Leave ordinary amide omega torsion terms unscaled; keep the
documented proline-like branch eligible for scaling.

When enabled, block production if an amide candidate cannot be classified reliably.

When disabled, scale all otherwise eligible solute torsions, do not apply omega exclusions, and
do not block merely because omega classification is unavailable.

Record the excluded central bonds, classification method, proline-like treatment, and final
boolean setting in the prepared-system/run metadata.

Describe the method neutrally as “REST2 with omega exclusion enabled by default” or
“omega-selective REST2.” Do not describe it as a new invention.

Add tests for the default-on behavior, --omega-exclusion false, proline-like bonds, N-methylated
ordinary amides, unclassified candidates, configuration hashing, and incompatible resume after a
toggle.

Conventional MD must be a first-class public workflow

As part of removing the old CLI identity, expose conventional explicit-water MD through
md-openmm, not only internal Python functions or documentation scripts. At minimum provide:

md-openmm validate-env
md-openmm validate-system
md-openmm prepare
md-openmm md
md-openmm rest2
md-openmm resume
md-openmm smoke

The md and rest2 commands must share bundle validation, run naming, chunk planning, provenance,
continuation checks, reporter conventions, and status semantics where scientifically appropriate.

Required tests and validation

At minimum, implement and run:

Pure unit tests for schema validation, chunk arithmetic, naming, fingerprints, salt accounting,
omega configuration, and exchange-log reconstruction.

Serialization tests verifying configuration/manifests survive round trips without changing
types or values.

CPU integration tests for a tiny explicit-water conventional-MD run and a tiny REST2 run.

Stop/resume integration tests for both methods.

A package build/install test from a clean environment that invokes md-openmm --help and a CPU
smoke test without relying on the source checkout.

A repository scan demonstrating that old names and AIS-only scope are absent.

If the full scientific environment is unavailable, run all environment-independent tests and
clearly list the exact commands that remain for the target OpenMM environment. Do not replace a
real integration test with mocks when the behavior being tested is OpenMM State/checkpoint/box
semantics.

Definition of done

All of the following must be true:

A named fresh run has no automatic timestamp; an unnamed fresh run does.

A continuous simulation resumes in the same directory and preserves step/time/history.

An incompatible continuation is refused before simulation output is modified.

Chunk count and chunk length are explicit inputs; totals are derived without rounding.

REST2 lifetime statistics remain correct after one or more resumes.

The equilibrated structure contains the same selected NPT box as the serialized State.

Counterions and salt pairs are reported separately and tested for charged solutes.

The generic package imports as md_templates and the CLI is md-openmm.

Conventional MD and REST2 are both public CLI workflows.

No obsolete project-identity or standalone AIS references remain in active files or paths.

Omega exclusion is enabled by default and can be explicitly disabled with
--omega-exclusion false.

Documentation and shipped examples use the new schema and commands.

Tests pass, and the final report lists changed files, deleted files, migration notes, test
commands, results, and any remaining scientific validation gates.

Do not proceed to unrelated enhancements until these conditions are satisfied.
