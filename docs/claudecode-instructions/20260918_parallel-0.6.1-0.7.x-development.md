REST2 tau. Never use the same parameter name or numerical value to mean both.

## 5. Branch 0.6.1: selective explicit-solvent REST2

Aim: scale chosen protein backbone/sidechain regions and chosen ligand instances while preserving
the physical tau=0 system and the established full-solute behavior when no new selection is given.

References: R1, R2, R3, and the current REST2 and ligand source files listed in section 10.

### User interface and resolution

Support mask strings:
~~~yaml
backbone_scaling_list: ":45,46,59"
sidechain_scaling_list: ":45-50"
ligand_scaling_dict:
  L01:
    mask: ":201"
    torsion_exclusions: "L01-exclusions.yaml"
  L02:
    mask: ":305"
    torsion_exclusions: auto
~~~

Also support the user's compact mapping `L01: <path-to-exclusion-file>` when L01 is an existing,
unambiguous recorded instance alias. If it cannot be resolved uniquely, require the explicit
entry; do not guess from the ligand residue name. Selecting one instance must not select every
copy of its compound.

Minimum mask grammar: numeric residue lists, inclusive ranges, and mixtures of them. Numbers are
one-based topology residue indices, not Python indices or PDB author IDs. Print the resolved
residue map and keep it with preparation. Chain qualifiers may be added through an existing
compatible parser; never claim the whole AMBER grammar if only a subset is supported.
Reject unsupported operators, unknown/out-of-range residues, ambiguous aliases, or empty matches
with an actionable error. Quote mask strings in YAML. Never invent per-chain index resets.

All new selector fields omitted means the legacy full-solute selection. If any new selector is
present, use explicit mode: only the supplied categories/instances are selected; omitted
categories mean none. Reject an entirely empty explicit hot region. Test this distinction.

The user may supply these settings through REST2 workflow configuration, but the authoritative
resolution and force construction remain in the build-time scaler. Plan and document how the
workflow config forwards them before state construction; reconcile duplicate declarations by
requiring agreement or rejecting them. Do not add runtime scaling or reuse stale rung XML files.

### Hamiltonian rules

- For selected atoms S and remaining atoms E, maintain nonbonded factors:
  S–S `(1-tau)^2`, S–E `1-tau`, E–E `1`, including exceptions and PME-consistent electrostatics.
- Resolve nonbonded atoms separately from torsion eligibility. A sidechain selection must cover
  chi1 even when its defining quartet includes backbone N/C-alpha. A backbone selection must
  handle phi/psi crossing a residue boundary.
- Document residue ownership of each central bond and scale all eligible proper Fourier terms
  belonging to that bond. Preserve the existing exclusions for ordinary amides, aromatic/double
  bonds, and impropers; preserve and document the existing proline-like exception.
- Define backbone/sidechain membership for hydrogens, termini, caps, glycine, proline, disulfides,
  and supported modified residues. Do not approximate unsupported chemistry silently.
- CMAP needs an explicit versioned rule. Proposed rule: scale a CMAP term only when both of its
  underlying backbone torsions are selected; leave a mixed selected/unselected pair unchanged
  and report it. Validate shared-map duplication and preserve legacy all-solute behavior.
- Bonds and angles remain unscaled. A torsion exclusion never removes its atoms from nonbonded
  scaling. Map ligand exclusions from package-local atom identities, not transferable global
  force indices. Save the resolved contents; an external path alone is insufficient provenance.
- Selective GB/implicit scaling is outside 0.6.1. Preserve supported whole-system implicit runs;
  refuse partial implicit selection before output.
- Version Hamiltonian identity when these selection semantics change. Refuse incompatible resume
  and stale saved-state reuse rather than mixing ensembles.

### Required evidence

Test analytic pair/exception factors, tau=0 identity, legacy-selection equivalence, phi/psi and
chi1 boundaries, multiple chains, two copies of one ligand, two distinct ligands, reordered atoms,
exclusion-file mutation, and CMAP shared/mixed maps.

Run actual CUDA explicit-solvent ladders for a small peptide and a protein–ligand fixture,
including selective backbone, selective sidechains, ligand-only, and combined selections.
Check direct exchange energies at stored coordinates, resume identity/refusal, standalone export,
and data registration. Preserve current NVT REST2 and MPI/MPS rules.

Do not use effective-temperature intuition as a substitute for testing the implemented energy.

## 6. Branch 0.7.0: conventional alchemy with Amber18 softcore

Aim: a reproducible topology-building, simulation, and analysis path for TI and FEP for absolute
and relative solvation/binding free energies, integrated with registered parameters and existing
MD-tools records. References: R4–R9.

### Milestones and topology scope

A0: written interfaces, input/output schemas, fixed reference fixtures, and OpenFE adapter choice.
A1: `md-openmm combine-topology`, explicit maps, combined coordinates, endpoint records, and
    single/dual/hybrid construction checks.
A2: validated Amber18 softcore Hamiltonian, complete state energies and derivatives.
A3: window execution, FEP/BAR/MBAR and TI, absolute and relative hydration examples.
A4: relative binding solvent/complex cycle and a validated simple ligand pair.
A5: absolute binding cycle with restraints, restraint free energies, and standard-state correction.
A6: integrated CUDA/CI, exports, registration, documentation, and installed-wheel validation.

These are staged milestones, not permission to silently remove binding or topology modes from
the user's 0.7.0 aims. Mark unsupported combinations explicitly until validated; do not claim a
complete 0.7.0 with release-required milestones unfinished.

Define terminology in AIMS:
- Single topology: one evolving atom representation with explicit handling of unmatched/dummy
  particles where supported.
- Dual topology: distinct endpoint ligand particle sets in one environment, with explicit mutual
  exclusions and positional/restraint treatment.
- Hybrid topology: a mapped shared core with separate endpoint-unique particles.
- Separated topology: intentionally deferred; do not implement or advertise it in this release.
Definitions must be based on particle representation and interactions, not just number of files.
OpenFE's hybrid machinery alone does not establish support for all three requested modes.

Start numerical fixtures with neutral ligands and charge-preserving, simple substitutions.
Before expanding chemistry, document validation requirements for net-charge changes/finite-size
corrections, ring changes, stereochemistry, constraints, virtual sites, covalent ligands, and
metals. Unsupported cases must be refused; never invent support from a successful short run.

### combine-topology

Keep construction independent of sampling and estimation. Accept registered endpoint parameters
and explicit or validated automatic atom maps. Preserve immutable parameter values and chemical
states. Generate reviewable maps, common/unique atom sets, combined coordinates, exclusions,
constraint/mass policy, and parameter/source hashes. Use one matched environment; independently
solvated endpoint boxes are not automatically atom-matched.

Validate mapping symmetry and chemical ambiguity, force-field compatibility, missing terms,
duplicate/omitted interactions, and endpoint recovery. Dummy partition-function contributions,
retained bonded terms, and restraint effects must cancel by a demonstrated construction or be
corrected explicitly. Comparing raw endpoint energies without accounting for dummy terms is
not a valid general endpoint test.

The CLI lives in the existing md-openmm executable. Reuse existing builder/configuration and
preflight authorities rather than making a second MD runner or parameter catalog.

### OpenFE reuse and Amber18 default

Use OpenFE as the implementation reference for mapping/hybrid construction, schedules,
cross-state energies, multistate sampling, and BAR/MBAR-compatible analysis. Prefer an adapter
around suitable pinned components over copying the whole project. Document any vendored code,
its license, commit, and deliberate differences.

Proposed canonical settings:
~~~yaml
alchemical:
  sc: true
  softcore_function: amber18
  scalpha: 0.5
  scbeta: 12.0  # angstrom^2; internal conversion is 0.12 nm^2
~~~

These are MD-tools defaults, not a claim that AMBER's native ifsc defaults to 1.
Support the Amber18 LJ and electrostatic softcore definitions in its manual section 21.1.5,
equations 21.5–21.7, with the paper R4 as the implementation reference. Define appearing and
disappearing directions and every intramolecular/exception rule.

OpenFE's default Gapsys potential, or selecting its Beutler LJ option alone, is not full
Amber18 equivalence. Validate electrostatic softening with the correct PME decomposition,
self/background terms where applicable, exclusions, and dispersion corrections. Do not merely
soften a real-space Coulomb term while accidentally retaining its original contribution elsewhere.

Separate the softcore functional form from the lambda schedule. Record whether electrostatics
and sterics change together or in stages. Validate the initial chosen schedule and explain it.
Do not implement a later AMBER smoothstep variant under the name "amber18".
`sc: false` must select a documented ordinary path for supported cases; reject unsafe/unsupported
particle insertion/removal combinations rather than silently re-enabling softcore.

### TI and FEP use one Hamiltonian

Write cross-state reduced potentials with explicit sample/state IDs for FEP, BAR, and MBAR.
Use stable exponential averaging for the requested FEP estimator and report overlap limitations.
BAR/MBAR and TI are analyses of the same defined path, not independent potential implementations.

For TI, report the complete derivative along path progress s:
`dU/ds = sum_k (partial U / partial lambda_k) (d lambda_k / ds)`.
Include softcore, electrostatics/PME, exception, bonded, restraint, and applicable long-range
correction terms. OpenMM custom-force derivatives alone do not prove complete coverage of
NonbondedForce parameter offsets. Use justified analytic or controlled numerical derivatives,
with documented error and finite-difference checks over multiple step sizes.

Do not reuse the existing AIS identity `dU/dlambda = U1-U0` for a nonlinear softcore path.
Preserve the original AIS mode; future alchemical AIS needs a separately defined contract.
If switching work is used later, its definition remains the frozen-coordinate energy difference.

Run fixed-lambda windows first. Add exchange only through existing MPI/exchange authorities.
Preserve LangevinMiddle, established timestep/HMR validation, truthful CUDA selection,
transactional resume, and read-only failed preflight. Alchemical NPT support needs ensemble-
correct state energies and checkpoints; do not impose REST2's NVT rule on ordinary alchemy.

For absolute binding, implement the full thermodynamic cycle, suitable Boresch-style or otherwise
validated restraints, restraint attachment/release contributions, and standard-state correction.
For relative hydration include the vacuum and solvent legs. For relative binding include
solvent and complex legs with consistent orientation/sign conventions.

## 7. Planning branches 0.7.1 and 0.7.2

### 0.7.1: advanced alchemical sampling

Write separate aims and references for these dependent milestones:
1. FEP–REST2: compose alchemical coupling and selective REST2 in one defined Hamiltonian;
   specify exchange topology and cross-state evaluations. Prove reduction to alchemy at tau=0
   and to the intended REST2 state at physical alchemical endpoints. A generic scaler must not
   multiply arbitrary new custom forces without a term-by-term derivation.
2. EDS: multiple endpoint evaluations, stable log-sum-exp enveloping potential, energy offsets,
   smoothing parameters, derivatives, and endpoint reweighting. Compare toy energies/forces
   against independent arithmetic before molecular simulations.
3. RE-EDS: build on validated EDS; add offset/smoothing optimization, exchanges, sampling

   uses GROMOS; inspect its OpenMM references separately. Do not claim an imported pipeline
   supplies a validated PME OpenMM implementation.
4. ATM: prefer supported native OpenMM ATMForce when appropriate; use the linked plugin as a
   reference. Validate transfers, displacement geometry, PBC, restraints, softcore mapping,
   state energies, and free-energy corrections for each supported application.

References: R1, R4–R9, R10, R11, and R12. Keep each milestone independently testable.
No requirement to force EDS or ATM into a conventional lambda interpolation representation.
Keep common runtime/evaluation interfaces while allowing method-specific state coordinates.

### 0.7.2: grand-canonical water sampling

Aim: conventional and nonequilibrium GCMC water insertion/deletion, then combination with
validated alchemical/REST2 protocols. References: R13 and R14, plus their primary method papers.

Specify chemical-potential and standard-state conventions, sampling region/volume, proposal
probabilities, indistinguishability factors, ghost-particle identity, occupied-particle counts,
periodic boundaries, electrostatics, momentum treatment, and transactional accepted/rejected moves.
For nonequilibrium moves, specify protocol work, integrator/proposal reversibility, and any
required path-probability or shadow-work treatment. Reusing an AIS trajectory generator alone
does not establish a correct Monte Carlo acceptance rule.

Validation aims: ideal-gas number distribution against the analytic law; bulk-water chemical
potential/density reference under a matched water model; reversibility and rejected-move state
restoration; pocket occupancy convergence across initial occupancies; combined alchemical free
energies with correct ensemble bookkeeping. Conventional and nonequilibrium methods should agree
within statistical uncertainty where both are converged.

GrandFEP is a reference for integration of alchemy, REST2, and water sampling, not proof that
all its choices can be copied unchanged. Grand supports conventional and nonequilibrium water
moves. Broader ligand insertion/deletion is a later extension; initial scope is water.

## 9. Validation, completion, and reporting

Write the acceptance matrix before running long campaigns. Each row names a fixture, expected
quantity, independent reference, numerical/statistical tolerance, platform, command, and evidence.
Classify each as PASS, FAIL, BLOCKED (dependency/hardware), or NOT RUN. Missing CUDA/AMBER/license
access is blocked evidence; neither a skip nor successful CPU run is a CUDA/AMBER pass.

Minimum gates:
1. Documentation: no broken internal links from cleanup; one active branch instruction index;
   examples parse with the intended resolver; generated references match source.
2. Deterministic physics: analytic pair energies, forces, and derivatives; physical endpoints;
   mask boundaries; exceptions; constraints; dummy contributions; serialization and relocation.
3. Derivative checks: central finite differences in the interior and appropriate one-sided
   checks at endpoints, using several step sizes; report convergence and absolute/component
   errors so solvent background energy cannot hide a defect.
4. Cross-engine checks: fixed-coordinate AMBER comparisons for the claimed Amber18 path at
   lambda 0, 0.25, 0.5, 0.75, and 1 where supported. Match parameters, cutoffs/PME, exclusions,
   restraints, and corrections. Report intentional differences. Separately compare the OpenFE
   adapter with an OpenFE-matched path; different paths need not have equal interior energies.
5. Sampling: independent repetitions and uncertainty/overlap/convergence diagnostics for one
   small absolute hydration, relative hydration, relative binding, and absolute binding fixture.
   Define pass thresholds before sampling. Suggested free-energy agreement gate for matched
   simple references: absolute discrepancy below both 0.5 kcal/mol and three combined standard
   errors (including integration/reference uncertainty); add a justified numerical floor for
   effectively exact fixtures. Inconclusive uncertainty is not a pass; document and resolve it.
6. CUDA/runtime: actual finite-state propagation, correct exchange state mapping where used,
   interruption/resume, changed-state rejection, installed-wheel execution outside the checkout,
   export reconstruction, and full dataset registration.
7. Regression: existing cMD, whole-solute REST2, and two-state AIS retain their contracts.
   Run the repository's required CI lanes on the candidate integration commit. CPU lanes must
   explicitly deselect unavailable GPU/reference-data lanes according to current CI conventions.

Calibrate deterministic tolerances against documented precision/reference error BEFORE comparing
the new implementation; record exact thresholds in the matrix and justify any later change.
Do not weaken a tolerance after failure merely to pass. Do not delete failing tests to close a gate.
Fix the underlying implementation, rerun affected checks, and record final results.

Use small fixtures for development. Broaden testing only to satisfy a required gate or resolve an
identified risk. Do not launch expensive protein campaigns before deterministic checks pass.
A 10 ns trajectory or green unit-test CI alone is not proof of a free-energy method's correctness.

Every completed milestone must have an implemented artifact, an executable example, and evidence.
For the current bootstrap, report the four actual branch URLs, docs-cleanup commits, branch aims,
contract commit, worker branches/worktree paths, complete session prompts, and first runnable jobs.
For subsequent integration, report implemented behavior, tested behavior, unresolved blockers,
and the next concrete assignment. Never describe planned work or another session's unverified
claim as complete.

## 10. Reference register and starting files

Pin software versions/commits when implementation begins. These links identify the intended
references; inspect their actual current APIs, licensing, and limitations before reuse.

- **R1 — REST2:** Wang, Friesner, and Berne, "Replica Exchange with Solute Scaling: A More
  Efficient Version of Replica Exchange with Solute Tempering (REST2)" (2011).
  https://doi.org/10.1021/jp204407d
  Use for scaling/exchange theory; MD-tools' explicit torsion exclusions are additional policy.
- **R2 — AMBER masks:** https://amberhub.chpc.utah.edu/atom-mask-selection-syntax/
  Use for syntax/numbering and supported-subset documentation.

  Baseline inspected at the SHA in this document; reread newer source before editing.

  in Amber18: Performance Enhancements and New Features" (2018).
  https://doi.org/10.1021/acs.jcim.8b00462

  Section 21.1.5, equations 21.5–21.7, softcore masks/parameters and interaction conventions.
