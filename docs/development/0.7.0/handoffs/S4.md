## Incidents

- **An S4 test run held a context on all nine GPUs** (18 GB on card 0, which belongs to
  TarFlow). pymbar 4 imports JAX, and JAX preallocates on every visible device. MD-tools-0.6.0
  noticed it. Fixed in `d80a0bd`: `PYMBAR_DISABLE_JAX` is pymbar's own switch, and it changes
  nothing for any other JAX user. MBAR records which backend ran. Every S4 run since then uses
  `CUDA_VISIBLE_DEVICES=""`. MD-tools-0.6.0 had pointed out that a first version, setting
  `JAX_PLATFORMS=cpu`, was a process-wide device decision made outside `platform_policy`, so it
  was replaced.

## Known limitations (not claims)

- NPT is shown on CPU only (N1). On CUDA it is BLOCKED like every other window row.
- **CUDA resume exactness is unknown.** CPU resume is byte-identical (W4). On CUDA it may be a
  new realisation, as AIS's is; that is to be measured, not assumed (row G1, BLOCKED).
- **Windows are independent.** There is no Hamiltonian replica exchange between windows. If it
  is added, it goes through `md_tools.remd` and its MPI authority.
- **The pairwise BAR path total** sums neighbour variances and ignores the correlation through
  shared windows. This is stated in the result.
- **Legs in a cycle are assumed independent** (separate simulations). The analytic release term
  carries zero variance, being quadrature.

## The entry point S4 would want `md-run` to call (for S0, request 3)

```python
# md_tools/alchemy/windows.py -- the analogue of stage_main / replica_main / ais_main
def window_main(window: dict[str, Any], argv: list[str] | None = None, *, prepared=None) -> int:
    """Run one fixed-lambda window. `window` is the resolved declaration from resolved.config:
    window_id; the path record (paths.py); every state (samples.ThermodynamicState records);
    WindowSettings; how the Hamiltonian is rebuilt WITHOUT a live Context (the topology-plan
    path and digest, the softcore settings, the restraint record if any); timestep and
    ensemble. argv carries the Amber-like flags: -p -s -c -o -log -r -odir, --cpu, --device,
    --overwrite, --check. There is no -x until a trajectory stream is added."""
```

Contract for it, which `run_window` already follows except where noted:
- It runs `preflight_stage` itself and CONSUMES the result: the platform, the machine settings
  and the loaded System, which it does not re-resolve. `prepared=` lets `md-run` hand over a
  result it has already checked, exactly as `stage_main` does. `run_window(prepared=...)` does
  this; a test makes a re-plan fail.
- The Hamiltonian is rebuilt from the `-s` System and the plan record, and its serialisation is
  compared with `-s` before anything is written. That comparison exists today.
- `--check` returns `report_check(...)` after the read-only continuation validation, and creates
  nothing: `run_window(check=True)`, tested.
- A continuation is validated read-only first: completion manifest, checkpoint fingerprint,
  committed prefix. `validate_public_entry`/`md_tools.run.continuation` should gain a window
  case that calls `validate_stream_prefix` and `verify_window`, so that `md-run` and a
  generated `window.py` refuse identically.
- Serial: a plural launch is refused by `preflight_stage(serial=True)`. Windows run as separate
  processes, and a campaign's provenance is each window's state.
- The output names are `window_paths(out_dir, window_id)`: `.out` and `.log` are two files, and
  the `.log` is the machine record.
