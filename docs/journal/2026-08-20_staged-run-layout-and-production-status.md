# 2026-08-20 — Production run status, and the staged run-layout the current design does not provide

Two things are recorded here together, deliberately: what the current monolithic design actually
produced, and the layout the user wants instead. The second is a **design wish, not implemented** —
it is written down so the next steps can be planned against a concrete description rather than a
recollection.

## Part 1 — the requested layout (NOT IMPLEMENTED)

### The problem with what exists

Today the whole chain is compacted into a small number of CLI invocations:

```bash
md-openmm prepare --config c.json --out-root ./bundle      # minimise + NVT + NPT, all inside
md-openmm md      --bundle B --config c.json --out-root ./md
md-openmm rest2   --bundle B --config c.json --out-root ./rest2
```

`prepare` runs minimisation, NVT and NPT **inside one command** and emits a single bundle. The
consequences, all observed in this session:

- only two of the three equilibration stages leave a structure behind (`eq_minimized.pdb` and
  `eq_equilibrated.pdb`); the **NVT endpoint has no coordinates written**;
- the equilibration `StateDataReporter` wrote **3 CSV rows** for the entire equilibration, so there
  is essentially no time-resolved trace of how the box settled;
- there is no per-stage directory, so a user cannot inspect, rerun, or hand off one stage;
- there is no generated script showing what was run, so the command a reader must reproduce lives
  in a shell history rather than in the project.

### The requested structure

```text
{project_name}/
    run_all.sh                  # executes the .sh in each stage folder, in order
    log                         # records what has been executed
    inputs/                     # generated by MD_input_gen.py
    min/
        min.json                # parameters + input topology + input coordinates, generated by
                                #   MD_system_gen.py
        min.sh                  # `python $openmm_script/min.py --config min.json`
        *.pdb  *.xml  *.json    # outputs: structure, checkpoint/state, results
    eq_nvt/
    eq_npt_1/
    eq_npt_2/
    cMD_1/
    rest2_1/
    ...
```

Rules the user stated:

1. **Every stage is its own folder**, named for the stage.
2. **Every stage folder holds its own inputs and outputs**: a `.json` config, a `.sh` launcher,
   and the resulting `.pdb`, `.xml` (checkpoint/state), `.json` (results) and logs.
3. **`{stage}.sh` gives the clear, explicit command** that launches that stage, e.g.
   `python $openmm_script/min.py --config min.json`. The command is a readable artifact, not
   something reconstructed from a shell history.
4. **The project root contains only two things**: a bash file that executes each stage's bash file,
   and a log recording what has been executed.
5. **Two generators, with separate jobs**:
   - `MD_input_gen.py` -> `{project_name}/inputs/`
   - `MD_system_gen.py` -> `{project_name}/{min, eq_nvt, eq_npt_1, eq_npt_2, cMD_1, rest2_1, ...}`
6. Stage `.json` records the stage parameters **and** the input topology and coordinates, so each
   stage states what it consumes rather than inheriting it implicitly.

### Why this is a real improvement, not a reorganisation

- **Each stage becomes independently rerunnable.** Today a failed NPT means re-running `prepare`,
  which redoes minimisation and NVT too. For RGDfV that is 27 minutes of AM1-BCC each time.
- **Every stage leaves evidence.** The missing NVT structure is a symptom: stages that own a folder
  naturally write their endpoint into it.
- **The launch command is a committed artifact.** `min.sh` is reviewable and reproducible; a CLI
  invocation typed once is not.
- **Numbered stages express a real protocol.** `eq_npt_1` / `eq_npt_2` and `cMD_1` / `rest2_1` say
  that a protocol may have several NPT phases and several production blocks — which the current
  single `equilibration` block cannot express.

### Design questions to settle before implementing

- **Where does the canonical configuration live?** The repository's central rule is that every input
  syntax resolves into ONE canonical typed model before a System is built. Per-stage `min.json`
  files must be *projections* of that model, not a second configuration engine.
- **What carries between stages?** A stage's `.json` naming its input topology and coordinates makes
  the chain explicit, but the hand-off state (positions, velocities, box vectors) must be a real
  file the next stage reads — the equivalent of today's `equilibrated_state.xml`.
- **What replaces the bundle?** The bundle is currently the unit of portability and hashing
  (`system_build_sha256`, `checksums.json`, relocation validation). A staged layout must keep an
  equivalent, or portability and tamper-detection are lost.
- **How does REST2 fit?** `rest2_1` is one segment or one run? The segment contract says a run is
  many segments in ONE directory, resuming from a committed generation. A per-segment folder would
  contradict that; `rest2_1` should probably be one run directory containing its segments.
- **Restart semantics.** The committed-generation record is the sole authority for the restart
  boundary. Per-stage folders must not introduce a second way to infer where to resume.

### Related open item

The instruction specifies **restrained** minimisation, NVT and NPT at 1 kcal/mol/A^2 with the initial
solute coordinates as reference. The examples use the `simple` equilibration protocol, which records
`restraint_k: 0.0` throughout — so the production runs below were prepared **unrestrained**. This was
not flagged when the examples were written. The `staged` protocol is the one with a restraint release
schedule. Changing it requires re-preparing both bundles.

## Part 2 — production run status

Both worked protocols were launched on the workstation at 07:45:42 with the exchange schedule
changed to `n_exchange_per_segment: 1000` x `exchange_interval: 5 ps`, HMR 3.024 amu, 4 fs.

Device allocation, at the user's request:

```
alanine   6 replicas -> GPUs 1,2,3       (2 replicas per device)
RGDfV    10 replicas -> GPUs 4,5,6,7,8   (2 replicas per device)
```

### Throughput, and a correction to the earlier benchmark

| | benchmark (1 ns segment) | production (5 ns segments) |
|---|---|---|
| alanine | 398 ns/day per replica on 6 GPUs | **~480 ns/day per replica on 3 GPUs** |

Faster on half the GPUs, which is impossible — so the benchmark was wrong. It timed a **1 ns**
segment including per-invocation setup (system build, per-replica scaled-System construction,
pre-exchange relaxation). Amortised over 1 ns that fixed cost dominates; over 5 ns it does not.

**The earlier figures of 398 and 143 ns/day understate steady-state throughput and should not be
quoted.** Benchmarks must use production segment lengths. The prediction that 3 GPUs would run at
"half of 398" was wrong on both the baseline and the model.

Alanine completed 5 ns segments in **15 minutes each**.

### Exchange acceptance — the first statistically meaningful figures

| system | attempts | overall acceptance |
|---|---|---|
| alanine | 6,643 | **0.480** |
| RGDfV | 3,672 | **0.299** |

Alanine's rate was 0.478 after segment 1 and 0.479 after segment 2 — stable to three decimals across
5,000 attempts, so this is a determined number rather than noise. Earlier figures from the benchmark
runs (0.400 and 0.389, from 10 and 18 attempts) carried no information and should be ignored: with
2 attempts per pair the only achievable values were 0.00, 0.50 and 1.00.

**Interpretation.** RGDfV's 0.299 sits squarely in the conventional 20-40 % target band. Alanine's
0.480 is above it, meaning its tau rungs are closer together than strictly necessary — replicas mix
readily, but six replicas may be spanning a range that fewer could cover. That is a ladder-design
observation, not a fault. A per-pair breakdown is needed before acting on it: an even 48 % across all
five pairs means something different from a mix of 80 % and 20 %.

Note the exchange cadence changed in this run from every 50 ps to **every 5 ps**, with 1000 attempts
per segment instead of 100, so these rates are not comparable to any earlier configuration.

### Status at the time of writing

```
ala: 6,643 attempts (2.66 of 3 segments), 2 committed generations
rgd: 3,672 attempts (0.82 of 3 segments), 0 committed generations
```

Alanine's two committed generations demonstrate the segment contract at production scale: segment 2
resumed from segment 1's committed generation via `--resume-run`, in the same run directory.

### What these runs are and are not

They are an operational demonstration that the chain runs end to end on real hardware at production
scale, and they give real acceptance statistics. They are **not** scientific validation: 10-15 ns per
replica is short, the systems were equilibrated unrestrained contrary to the instruction, and no
convergence assessment has been made. Nothing here should be quoted as evidence about macrocycle
conformational ensembles.
