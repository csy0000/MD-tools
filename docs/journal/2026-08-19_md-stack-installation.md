`install-md-stack` skill. Both `pmemd.cuda` and `pmemd.cuda.MPI` are built and working;

## Findings worth keeping

### The conda channel matters

conda-forge's AmberTools has **no CPU-parallel and no CUDA support**. Only the `dacase`
channel build does. Getting this wrong silently produces a serial-only AmberTools.

### CUDA version is decided by Amber's own CMake, not by folklore

`cmake/CudaConfig.cmake` requires CUDA `>= 7.5 and < 12.9` and gates the CUDA/host-compiler
pairing. It contains an explicit special case permitting **gcc 13.3 with CUDA 12.6**, which is
what we used. Read that file from the release being installed; the ceiling moves between releases.

### Five build defects, four of them from pairing Amber with a conda toolchain

| symptom | cause | fix |
|---|---|---|
| `Could not find Fortran compiler gfortran` | conda ships only `x86_64-conda-linux-gnu-gfortran` | install unprefixed `gcc`/`gxx`/`gfortran` wrappers |
| `C::Math` target not found | conda toolchain never searches its own sysroot for `libm`; the system `libm.so` is a linker script that fails under `--sysroot` | `-DCMAKE_LIBRARY_PATH=<sysroot>/lib64;<sysroot>/usr/lib64` |
| `cicc: not found` | CMake auto-selected `targets/x86_64-linux/bin/nvcc`, a non-functional copy | pin `CUDA_TOOLKIT_ROOT_DIR` and `CUDA_NVCC_EXECUTABLE` to the env root |
| `Could NOT find CUDA (missing CUDA_INCLUDE_DIRS)` | `FindCUDA` looks for `device_functions.h` under the root; conda puts headers in `targets/x86_64-linux/include` | set env `CUDA_PATH` to the targets dir |
| 46 undefined `libstdc++` symbols from `libemil.so` | EMIL is `project(emil CXX)` with no link interface, linked into every pmemd target (including the CUDA ones) while pmemd links through `gfortran` | append `-lstdc++` to `CMAKE_Fortran_STANDARD_LIBRARIES` |

The third and fourth are in tension: `nvcc` only works from the env root, headers only exist
under `targets/`. The working combination points the two variables at **different** directories.

### 82% of Amber's test suite silently did not run

`/bin/csh` is absent on this machine and **670 of 819** `Run.*` scripts start with `#!/bin/csh -f`.
`make` logged each as `Error 127 (ignored)` and continued, so the harness reported clean runs over
a fraction of the tests — 86 skipped per run. The first three test runs (reported at the time as
passing) covered roughly 18% of the suite.

Fixed by repointing 720 shebangs in the *installed test tree* to the conda `tcsh` already present
in the build env. Interpreter path only; script bodies, inputs and reference outputs untouched.
Reversal manifest at `manifests/csh-shebang-rewrite.txt`.

**Lesson: an ignored non-zero exit is not a pass. Check the skip count, not just the pass count.**

### Stale reference data explains most failures

None of the non-ignorable failures involved an energy discrepancy:

- **NEB tests**: references generated by **Amber 16 in 2018** on a Blue Waters node. Diffs are the
  version banner, run date, hostname, allocation counts and timing percentages. Zero energy lines differ.
- **`nfe/abremd`**: reference echoes `ntx = 7` while the shipped `mdin.1`–`mdin.4` all specify `ntx = 5`.
- **`rem.log`**: our output carries extra RREMD/reservoir header lines the reference predates.
- No GTI reference anywhere in the tree was generated by Amber 26; they span Amber 16–24.

### SPFP is correct — the failure count was misleading

Initially flagged as a possible defect. It is not. `dacdif` reports the maximum relative error
anywhere in a file, including near-zero fields and end-of-run coordinates that decorrelate
chaotically. Per-step comparison settles it:

```
step   reference        ours             abs diff
1      -440315.5400     -440315.5400     0.000e+00
2      -440315.5400     -440315.5400     0.000e+00
3      -438410.9012     -438410.9042     3.000e-03   (relative 6.8e-09)
8      -433388.0698     -433388.0732     3.400e-03   (relative 7.8e-09)
```

Bit-identical for two steps, then agreeing to ~9 significant figures. That is last-bit rounding
amplified by Lyapunov divergence — unavoidable, since SPFP rounds differently on different GPU
architectures and Amber's references were generated on the developers' hardware. DPFP passing
325 comparisons at a `1e-7` tolerance is the proof the kernels are right.

**SPFP needs no action and is safe for production use, including alchemical free energy.**

## Open issue: SGLD is broken under MPI (upstream bug, diagnosed)

`pmemd` aborts during setup with `atommask.f::pop_evalstack / stack underflow` whenever SGLD runs
under MPI. Failure surface:

| | serial | ≥2 ranks MPI |
|---|---|---|
| CPU | OK | **FAIL** |
| GPU | OK | **FAIL** |

Root cause, from the source:

1. `sgmask` is declared `character(1024)` (`mdin_ctrl_dat.F90:294`).
2. Its default `sgmask=':*'` is set in `init_mdin_ctrl_dat`, called from `master_setup.F90:230` —
   **master rank only**.
3. `bcast_mdin_ctrl_dat` broadcasts integers, doubles, PHMD arrays and `plumedfile`. It does
   **not** broadcast any mask variable.
4. The only synchronisation is `sgld.F90:301`, which broadcasts **256** characters:
   `call mpi_bcast(sgmask,256,MPI_CHARACTER,0,pmemd_comm,ierror)`
5. Bytes 257–1024 remain uninitialised on non-master ranks; `atommask()` parses the garbage.

One-character fix: `256` → `1024`. **Not applied** — patching licensed source would invalidate the
validation snapshot. Worth reporting upstream.

Affects `rxsgld` and `sgld` under MPI only. Does not affect REST2, standard REMD, or conventional MD.

## Next steps

### 1. Input-file generator (`md_in_generator.py`) — the priority

Build a generator that takes a small set of user inputs and emits everything needed to run the same
simulation in **both** Amber and OpenMM. This is the natural next piece: the stack is installed, and
what is missing is a reproducible way to define a run once and target either engine.

Design discussion is happening separately; details to be settled before implementation.

### 2. Do not cross-validate Amber against OpenMM by single-point energy

An earlier suggestion to compare Amber and OpenMM energies directly was **wrong** and is withdrawn.
The engines differ in PME mesh and spline defaults, exclusion handling, long-range dispersion
corrections and constraint algorithms, so exact energy agreement is not a meaningful criterion.
Any cross-engine comparison should be at the level of **ensemble properties**, not single-point energies.

### 3. Hardware confidence checks, before production

- **Per-GPU health check** — an identical short job on each of the eight 3080s, comparing energies.
  A single degraded card silently corrupts replica exchange, and devices 2–8 have only ever been
  exercised collectively, where one bad GPU hides in the aggregate.
- **Determinism check** — the same job twice on one GPU; SPFP is bitwise reproducible on identical
  hardware, so any difference means flaky memory.
- **Sustained thermal stability** — consumer 3080s throttle and have **no ECC**, so a bit-flip in a
  long REMD run is silent.
- **Memory headroom** — largest system that fits in 10 GB, which determines whether production
  systems need the A5000's 24 GB.

### 4. Close the coverage gaps

Run the AmberTools test suite and `make test.serial`.

## Constraints that bear on `md_in_generator.py`

### `openff-interchange` can already export to both engines

This is the most important finding for the generator. In `openfftools`:

```
Interchange exports: ['to_openmm', 'to_prmtop', 'to_inpcrd', 'to_amber', 'to_gromacs']
```

A single parameterised `Interchange` object can emit Amber `prmtop`/`inpcrd`, an OpenMM `System`,
and GROMACS input. That is precisely the "define a run once, target either engine" capability, and
it means the generator does **not** need to hand-write two independent input paths.

This supersedes an earlier note in this journal saying no environment could import both engines'
Python APIs. That was true before `openfftools` existed; it is no longer true.

### numpy is split across an ABI boundary

- `ambertools26`: **numpy 1.26.4**
- `openmm8` / `openfftools`: **numpy 2.5.2**

These straddle the numpy 2.0 ABI break. The environments cannot be merged by `conda install`;
something would have to be rebuilt or downgraded. Any generator that needs both `parmed`/`tleap`
**and** `openff`/`openmm` in one process has no home today.

### What is missing

- **`mdtraj` is in no environment.** If the generator or downstream analysis needs it, that is a new
  dependency decision.
- **`tleap` and `cpptraj` exist only in `ambertools26`**, which is also the only env on numpy 1.x.
  A generator running in `openfftools` cannot call them in-process; it would have to shell out.

### Practical implication

Two plausible designs, both viable:

1. **Generator lives in `openfftools`** and uses Interchange for everything, shelling out to
   `ambertools26`'s `tleap`/`cpptraj` only when Amber-native preparation is genuinely required.
2. **Generator writes input files only** and imports neither engine, in which case it can live
   anywhere — the most robust option for pipeline invocation, since a script can always be run as
   `<env>/bin/python md_in_generator.py` with no activation at all.

The choice depends on whether the generator needs to *parameterise* systems or only *emit control
files*. That is the question to settle before implementation.

## Two defects found while reorganising

**MPI launcher mismatch in the activation script.** AmberTools' conda env ships its own Open MPI
(5.0.10) and puts `mpirun` on `PATH`; `pmemd.cuda.MPI` is linked via rpath against `amber-build`'s
Open MPI (**5.0.8**). Sourcing the activation script therefore selected a launcher that did not
match the linked library — exactly the build-time/run-time MPI mixing the skill warns against. All
validation runs in this journal were unaffected because they set `PATH` explicitly. Fixed by
prepending `amber-build/bin`, which also restores `nvcc`/`gcc` from the toolchain the stack was
compiled with.

**`PYTHONPATH` leak between two Python 3.12 environments.** `ambertools26/amber.sh` exports
`PYTHONPATH` to its own site-packages; any later `python` on `PATH` inherits it, including OpenMM's.
The activation script now `unset`s it, and `installation/README.md` section 7 was corrected to match.
