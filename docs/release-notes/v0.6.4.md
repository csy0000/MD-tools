# 0.6.4 — the alchemical transformation, as far as it actually goes

This release makes alchemical free energies work from the command line and checks the answer
against something outside the code. `combine-topology` writes a plan, `build-md` generates a
runnable ladder from it, `run.sh` runs the windows on as many cards as you have, and MBAR turns the
samples into a free energy. The result has been validated two ways: against an experimental number,
and against a completely different alchemical route through the same thermodynamics.

**No existing protocol changes.** cMD, REST2, AIS and umbrella are untouched. `protocol:
alchemical` is a new value; every configuration that resolved in 0.6.3 resolves identically.

## `protocol: alchemical` resolves

`build-md` accepts an `alchemical` section:

```yaml
protocol: alchemical
alchemical:
  plan: ./plan                    # what `md-openmm combine-topology` wrote
  lambda_path: linear             # `staged` is refused; see below
  number_of_windows: 12           # or lambda_values: 0.0, 0.25, 0.5, 0.75, 1.0
  window_steps: 500000
  equilibration_steps: 10000
  report_interval_steps: 500
  checkpoint_interval_steps: 50000
```

and `md-run` parses the matching `&alchemical` block. Every `.in` round-trips back to exactly the
`resolved.config` beside it, both ways of placing the windows included — the same contract the
other four protocols keep, and a test rather than a convention.

Nothing in the section restates a fact the plan already holds. The two end states, the atom map,
the environment and the combined numbering are in the plan, which carries its own digests and is
validated where it is LOADED. A second copy here would be the one that drifts.

**`lambda_path: staged` is REFUSED, and the missing piece is a scientific decision rather than
code.** A staged path moves electrostatics and then sterics; this Hamiltonian also moves
`lambda_bonded`, and which stage carries it changes the path every window samples. Under the
default `junction_policy: retain-all` no bonded force differs between the end states, so no
λ_bonded-dependent force is CONSTRUCTED and the placement changes nothing — while under
`separable`, or a hybrid whose common core genuinely changes bonded parameters, it changes every
window's ensemble. **The choice would be invisible exactly when it is harmless and silent exactly
when it is not**, which makes a default dangerous rather than merely unagreed. `linear` — the
Amber18 one-step diagonal — is what the campaigns use.

The arithmetic a staged path needs is already written and held as five `xfail(strict=True)` tests:
the day it is wired they XPASS and the lane fails, which is how the next person finds the
arithmetic instead of deriving it again. **A window must sit exactly on the knot** — the slope of
every λ component jumps there, so dU/ds has two values and no trapezoid drawn across it recovers
the integral; a count whose grid misses it is refused with the arithmetic that would fix it.

**Value-level refusals are delegated**, not restated. `SoftcoreSettings`, `WindowSettings` and
`md_tools.alchemy.paths` enforce their own rules at run time, and the configuration layer hands the
resolved values to them. A configuration therefore cannot accept a setting the node will refuse
three stages of equilibration later, nor refuse one the runtime would have accepted.

## And both surfaces run one

`build-md` generates the run directory and `md-run` dispatches into it. One dispatch,
`md_tools.alchemy.generated.window_main`, reached from both:

```bash
python w000.py                                              # one window
md-openmm md-run -i ../input/alchemical.in -odir . --window w000
./run.sh                                                    # all of them
```

A generated directory holds `resolved.config`, the plan copied in and content-addressed, `leg/`
(whose System is built ONCE at generation, with its digest checked at every window), one two-line
entry point per window, and `run.sh`. No `-p` and no `-s`: a window reads `leg/`, and offering a
`../build` path would be a second System for the same windows.

For most of this cycle both surfaces REFUSED instead, rather than fall through to the preparation
chain — which would have produced a `run.sh` that minimised, equilibrated and stopped, a
complete-looking run that sampled nothing. Those two refusals were the acceptance criteria for the
work that replaced them, and the tests that asserted them now assert what they became.

An input naming a preparation `stage` is unaffected: `stage` decides, not `protocol`, and
minimisation is minimisation.

## `mode: decoupling`, and a tutorial that runs

`combine-topology` had three modes -- `single`, `hybrid`, `dual` -- all of which turn one ligand
into another. `build_decoupling_plan` had existed in the library since the plan builder did, so
**the simplest alchemical calculation there is, removing one molecule from water, was reachable
only from Python.** It is now a mode:

```yaml
mode: decoupling
endpoints:
  A: {parameters: ./build/parameter}
```

Endpoint B is the ligand ABSENT, so `endpoints.B`, `b_pose`, `map.file`, `map.automatic` and
`dual.restraint_k_kj_mol_nm2` are each refused BY NAME. A `map` silently ignored here is a mutation
somebody wrote and set the wrong mode on, and it would run as a decoupling without a word. The CLI
calls `build_decoupling_plan` rather than `build_topology_plan(mode="decoupling")` precisely because
the net-formal-charge refusal lives in the former -- a charged ligand changes the box's net charge,
and PME's neutralising background then needs a finite-size correction this release does not
implement. The plan builds either way, so reaching past that entry point would lose the check
silently; a test asserts the refusal survives the trip through the configuration layer.

**The CLI plan is bit-identical to the one the validation campaign ran** (`plan_sha256`
`29c233c0...` from both paths). That is the test that matters: a CLI building a merely similar plan
would make the tutorial's commands describe a different calculation from the one the published
numbers came from, and nothing would say so.

Two defects came out of insisting the tutorial be runnable as written, neither of which any test
would have caught:

* **`build-md` crashed on every decoupling plan.** A decoupling's `endpoints.B.reference` is `None`,
  and that went into the path constructor: `PathError: a path names both endpoints`, raised AFTER
  the plan had been copied into the run directory, naming neither the plan nor the mode, for a
  configuration that was entirely correct. A decoupling's ends are now `coupled` / `decoupled` --
  the names `md_tools.alchemy.cycles` already uses, so a generated leg is comparable with the
  campaign's records.
* **`build-md`'s own log printed `end states ... -> None`**, and `LogWriter.field` used
  `{key:<28}`, which silently concatenates when a key is longer than the column:
  `plan.b663f7bf42da/combined.pdbmd_script/plan...` read as one path in the log a person checks a
  generated run against.

New tutorial: [ethanol / hydration free energy](../tutorial/ethanol/hydration.md), run as written
in 31 minutes on four cards. ΔG_hyd = **−3.648 ± 0.107** kcal/mol against the campaign's
three-repeat **−3.523 ± 0.025** -- the same number, 0.125 apart against a single-run σ of 0.107.

Its most useful section was not planned. **TI gives −4.195 while MBAR, BAR and both EXP directions
sit between −3.62 and −3.84.** Not a bug: TI trapezoids ⟨∂U/∂λ⟩ through twelve points, and near
s = 1 it varies too sharply for a 1/11-wide gap to follow. So the page teaches what estimator
disagreement DIAGNOSES -- TI away from MBAR means the λ spacing, EXP directions apart means the
exponential average is carried by its tail, MBAR away from BAR means the samples themselves. Four
estimators over identical samples are four probes of one measurement, and their pattern is the
diagnostic.

`tests/test_tutorial_hydration.py` lifts the page's YAML blocks out and resolves them through the
real resolvers, and checks the headline number against the campaign it claims agreement with. It is
the first test in the suite that does this to a tutorial; all three of its guards were shown to fail
before being trusted.

## What the runtime has been shown to compute

New page: [alchemy/validation.md](../openmm_methods/alchemy/validation.md).

Three FreeSolv molecules decoupled from TIP3P water, twelve windows, 1 ns each, three repeats —
nine legs, 108 windows, 108 ns on CUDA/mixed:

| ligand | ΔG_hyd, kcal/mol | ± (repeat spread) | experiment |
|---|---|---|---|
| ethane | **+2.478** | 0.033 | +1.83 |
| chloroethane | **+0.839** | 0.067 | −0.63 |
| ethanol | **−3.523** | 0.025 | −5.00 |

Ethanol is in the set because its hydration is dominated by the **charging** leg, which the two
weakly polar molecules barely exercise.

The check that matters is not agreement with experiment — a force field can miss that for reasons
that are not defects. It is that ΔG_hyd(chloroethane) − ΔG_hyd(ethane) obtained by DECOUPLING each
reproduces the same difference obtained by MUTATING one into the other: a different plan, different
end states, different particles appearing.

| route | ΔΔG_hyd, kcal/mol |
|---|---|
| decoupling each ligand | **−1.639 ± 0.074** |
| mutating one into the other | **−1.743 ± 0.026** |

**0.104 ± 0.079 apart, or 1.3 σ.** Consistent.

## A number this page nearly shipped

The first repeat alone gave −1.759 against −1.743 — an agreement to **0.016**, and it was written
into the validation page as the headline before the other repeats finished.

It was a coincidence of one realisation. Chloroethane's three repeats span 0.747 to 0.969, so any
single one lands about 0.1 from the mean by luck in either direction. **An agreement much tighter
than the reproducibility of the two things being compared is not a stronger result; it is a sign
that not enough of them have been run.** The caution is kept in the page beside the corrected
number rather than quietly replaced by it.

Two related corrections in the same page: the error bar is the REPEAT SPREAD, not MBAR's σ (which
is the within-run error at fixed sampling and cannot see what differs between realisations); and an
earlier claim that the spread exceeds the within-run error came from two points and is false at
three — spread/σ is 0.4 to 1.2, comparable, neither dominant.

## The self-check record carries its sample count

`evaluation_self_check_kJ_mol` is the largest disagreement between the evaluation Context and the
sampling Context over every report a window made. As a worst-case witness that is right; as a
number to compare BETWEEN windows it is not, because it grows with how many reports there were. A
longer window looks worse for being longer, and a plot of it across a ladder measures window
length.

The completion record therefore carries `evaluation_self_check_n` and
`evaluation_self_check_median_kJ_mol` beside it, and is **version 2**. Not a silent addition: two
shapes answering to one schema name is what a version string exists to prevent. `verify_window`
reads the fingerprint and the two digests and nothing else, so a version 1 window still verifies
and is not re-run.

The count also makes the resume scoping visible — a continued window's reporter starts fresh, so
all three numbers describe only the evaluations since the resume, which was already true of the max
alone and silently.

## Evidence

Fast lane: **2910 passed, 3 skipped, 5 xfailed, 0 failed**, 615 deselected.

`tests/test_alchemy_windows_cuda.py` on CUDA with the record change: 5 passed.

The softcore Hamiltonian's CUDA lane carries three known failures, deliberately, decided
2026-09-19: precision on a 2.4×10⁴ kJ/mol overlap term at λ = 1. Re-run here five times on a
different card and confirmed bit-identical to the 2026-09-21 evidence — the same energy, the same
derivative and the same force, digit for digit, which is what says they are deterministic
arithmetic rather than drift. A **fourth** failure appeared in one run of five, in the file that
propagates: its Langevin integrator and barostat are unseeded, so the configuration it compares at
differs every run. That one is not evidence of anything in either direction until it is seeded.
