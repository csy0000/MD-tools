# 0.6.0 — reusable ligand parameters, protonation you choose, and placement that measures

**Nothing is removed and nothing is renamed.** Every 0.5.4 configuration resolves unchanged, and
every command keeps its flags. One default moves — `solute.parameters` was absent and is now
`search` — and it changes what a build does only when a catalog is present to search.

## Reusable ligand parameter packages

Parameterising a ligand is the slowest part of a small-molecule build, and until now every build
paid it again. A **parameter package** — `molecule.sdf`, `parameters.ffxml`, `metadata.json` and a
browsable `parameter.config` — records one parameterisation so later builds can reuse it.

```yaml
solute:
  kind: complex
  parameters: search            # the new default: look, reuse on a match, parameterise otherwise
ligands:
  - select: {chain: A, resid: "2200", insertion_code: ""}
    parameters: CHEMBL112/param_e932f4c4f371
ligand_catalog:
  path: ../catalog
```

`solute.parameters` takes three kinds of value: `search` (the default), an explicit
`<compound>/<parameter>` reference, or `generate`.

**A match is decided on four things together** — the heavy-atom skeleton, the exact protonation
state, the charge method *with the implementation that produced it*, and the force field resource.
Charges are not interchangeable: AM1-BCC through AmberTools' `sqm`, through OpenEye and through
NAGL's graph model are three different results, so a package that cannot say which produced it can
be **named** and used, but can never be **found** by a search. `built.log` records which candidate
matched and why each other did not.

Charge software *versions* are recorded and deliberately not compared, so an AmberTools point
release does not invalidate a catalog.

See [ligand packages](../ligand-packages.md).

## Protonation is a stated choice, with PROPKA3 available

```yaml
protonation:
  method: propka                # or `openmm`, the previous behaviour and still the default
  ph: 7.0
  overrides:
    - select: {chain: A, resid: "102", insertion_code: ""}
      variant: HIE
```

`openmm` keeps what md-tools always did — `Modeller.addHydrogens(pH)` chooses. `propka` predicts
pKa values on the prepared structure and assigns variants by **one stated rule**: ASP/GLU
protonated when pKa > pH, LYS neutral when pKa < pH, HIS doubly protonated when pKa > pH and
otherwise neutral, with OpenMM's hydrogen-bond heuristic picking HID or HIE because PROPKA does not
resolve that tautomer. A predicted state no supported variant can build is **reported and the
standard state kept**, never silently approximated. PROPKA missing or failing is an error, never a
fall back. Everything lands in `build/protonation.json`.

Either way the states are fixed for the run: this is not constant-pH MD.

## Structures: assemblies and missing atoms

```yaml
input:
  assembly: "1"                 # expand an mmCIF biological assembly into distinct chains
  missing_atoms: add            # or `refuse`, the default
```

Biological assemblies expand into distinct chains, with on-axis ions and waters kept exactly once.
Crystal waters and ions are kept after the solute. Missing heavy atoms are refused by default, or
built when you ask.

**Deleting a crystallisation additive is an edit to your own file, not a build setting.** Strip the
residues before building and pass the edited structure to `-i`:

```bash
grep -v -E "^HETATM .* (EDO|SCN) " deposited.cif > prepared.cif
```

That edits the **deposited** ids, before any `input.assembly` expansion, so a residue present in
several copies goes from all of them — usually what you want for an additive. Record in your own
notes what you removed and why: the build no longer does. A configuration carrying the retired
`input.remove` key is refused with this migration rather than with "unknown key".

The prepared structure is saved beside the System as `built.prepared.pdb`, so a rebuild — and a
reference bundle — starts from exactly what was read.

## Concurrent CUDA: placement by measurement, and MPS

Workers are no longer dealt round-robin over devices. Placement **measures** each visible device
with this run's own System and maximises the slowest worker's share, because a synchronous ladder
runs at the pace of its slowest rank. A device that measures slow is given fewer workers or none.

**Measured**, at 23,659 particles: four workers on four cards are **1.32x** faster than the serial
ladder, and MPS makes four workers sharing one card **1.26x** faster than unmanaged sharing. At
1,760 particles concurrency *costs* time — the crossover is real. Sharing one card is still not
faster than using it serially: MPS buys that a ladder **runs** with fewer cards than replicas, not
that it runs faster.

A shared GPU without verified MPS is refused before anything is written, and the refusal now says
what is shared, where your rank stands, and the rates behind the decision:

```console
REST2: this launch shares device 3 between 2 workers. NVIDIA MPS is absent for this process; this
rank is alone on device 1, but the launch cannot proceed unverified: a ladder is synchronous, so
the shared device sets the pace for every rank.
  Workers were placed by: measured throughput (balanced). Measured steps/s at preflight: device 0
  13258, device 1 110828 ... Device 0 measured 9.4x slower than the fastest, so it was given fewer
  workers or none. A device measures slow because it is slower OR because something else on this
  machine is using it, and this measurement cannot tell those apart — check the card before
  concluding anything about the hardware.
```

That last sentence is there because it caught us: a card measuring 9.4x slow turned out to be busy
with an unrelated job. Idle, it was within **1.06x** of its neighbours. **Placement is a property
of the host at preflight time, contention included** — two identical launches minutes apart can be
placed differently, and one refused. The rates are in every refusal and in
`acceleration.placement.measurement`.

## Fixed

* **An umbrella window no longer opens on an unrelaxed structure.** The resume test interrupted
  inside the checkpoint transaction, then demanded a resume the contract correctly refuses.
* **A ligand refusal names the input you typed**, not the staged copy in a temporary directory that
  no longer exists by the time you read it.
* **A package written before `parameter.config` existed still loads**, and one whose declaration was
  written under an older schema is re-derived rather than read as a contradiction. A declaration
  under the *current* schema that disagrees with its parameters still refuses — that check is what
  catches an edited catalog.
* The umbrella platform guard asks whether a **device** exists, not whether CUDA is registered.

## Testing

The GPU lane needs **six visible devices** for
`test_multi_rank_rest2_ladders_of_several_sizes[6]`; everything else needs at most four. Run it in
two parts rather than exposing a mixed set, and give the MPS tests the daemon's own client-side
card numbering:

```bash
# six idle cards, ~4m30s
CUDA_VISIBLE_DEVICES=0,2,4,5,6,7 pytest tests/test_cuda_coverage_matrix.py \
    -k test_multi_rank_rest2_ladders_of_several_sizes

# four cards plus a scoped MPS daemon, ~14m30s
CUDA_VISIBLE_DEVICES=4,5,6,7 MD_TOOLS_TEST_CARDS=4,5,6,7 \
MD_TOOLS_TEST_MPS_PIPE_DIRECTORY=<the daemon's pipe dir> MD_TOOLS_TEST_MPS_CARDS=0,1,2,3 \
    pytest tests -m gpu -rs \
    --deselect tests/test_cuda_coverage_matrix.py::test_multi_rank_rest2_ladders_of_several_sizes
```

Use `-rs`: a lane whose tests all skip still exits 0, and the count is the only thing that says so.
