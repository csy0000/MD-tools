# 0.5.3 — an extension can run the group file an extension writes

Three fixes, all found by the hpREST2 campaign running this engine in anger, and all of the same
shape: **a default that means something specific, where nothing was meant.**

## An extension generated a group file its own parser rejected

`--extend-from` takes the physical state from the parent's checkpoint — positions, velocities,
box, the state-to-walker map, the RNG stream, the exchange count — so the group file it writes
correctly carries no `-c`. The parser required `coordinates` on every line regardless, so every
rank aborted:

```
replica executor: REST2.group:7: no coordinates given
[rank 0/6] fatal: REST2 rank 0: the executor returned 2
```

This stopped an explicit-solvent ladder at 100 ns/state that was asked for 500. Nothing exercised
the generated file against the parser that has to read it, which is how the two halves came to
disagree; `tests/test_extension_group_file.py` now does, including on the exact shape
`--extend-from` emits.

`coordinates` is now required only when an extension is *not* in force, and the refusal says so.
The other required fields are unchanged, a fresh ladder still cannot start without a starting
state, and a caller who passes `-c` on an extension anyway is not refused — the value is inert,
not forbidden.

### Both consumers of that group file had the same omission

Teaching the parser that a coordinate-free line is legal was half of it. `_announce` and
`run_grouped` still read `group["coordinates"]` unconditionally, so an extension aborted anyway:
every rank raised `KeyError: 'coordinates'` immediately after writing its header — which is worse
than the original refusal, because the run had already printed as though it had started — and, once
that was fixed, again one step later while building the driver's files.

Found by running an extension of a real two-rung ladder on the CPU, which is the first thing that
gets past the parser at all. The announcement now says where the state comes from (`-c (none:
continued from the parent's checkpoint)`) and `run_grouped` passes `None`, which is what an
extension means: positions, velocities, box, the state-to-walker map and the RNG stream all come
from the parent's checkpoint. Two tests: one drives `_announce` with the exact shape
`--extend-from` emits, and one refuses any unguarded `[...]["coordinates"]` anywhere in the
executor, because this was one omission in two places and the second only became visible once the
first was fixed.

### An interrupted extension is redone, not resumed

Making extensions usable surfaced the question immediately after: what happens when a segment is
interrupted half way? It holds a committed checkpoint and a run-state record, and no
`restart.json`, which is exactly the shape an ordinary interrupted run has — so `--resume` is what
anyone reaches for.

It is the wrong reach, and the two obvious routes fail in opposite ways. `--resume` together with
`--extend-from` is refused as two different operations, which sounds like a complaint about flags.
`--resume` alone, on the segment's own directory, does **not** fail: `_continue` would carry the
run to its budget and write a `restart.json` with no `extends` block at all, leaving a segment
that reads as an ordinary run with its parent pinning, segment-local counts and chain accounting
gone. With per-tau equilibration it cannot even get that far, because the missing-record excuse is
granted only to a state that carries `extends`.

So an extension segment is **atomic**, and atomic *by omission* rather than by a guard: no resume
path knows `extends` exists. The fix is not a new resume — it is telling the truth at the four
places that were advising `--resume` unconditionally: the clean-stop run-state note, the driver's
printed interruption line, the `DriverError` raised when a run stops short of its budget, and the
executor's stderr on status 130. Each now distinguishes an in-place run from a segment and, for a
segment, names re-running the whole thing with `--extend-from` into a fresh directory. Re-running
into the partial one is refused three ways already (`--force` is refused with `--extend-from`,
`--overwrite` does not apply, and the existing outputs collide), which is why *fresh* is stated
rather than implied.

`tests/test_extension_directory.py` now interrupts a genuine extension once a checkpoint is
committed, asserts the advice names the redo and never the resume, and asserts the parent is still
byte-for-byte unchanged; the `--resume` + `--extend-from` dead end is a test of its own. The
practical mitigation, for a chain long enough that this matters: several smaller `--extend`
segments, each extending the previous completed one, so an interruption costs one small segment.

## `-o`, `-log`, `-r` and `-chk` now default by segment

The trajectories, the state table and the per-force-group energies have carried a segment for
some time. These four did not, because they come from the command line and whatever path is
handed over is what gets written — and `SimOut` opens its file `"w"`.

So a second segment run in place with the same command line **destroyed** the first segment's
human-readable output and its provenance record, leaving a directory in which `mdout_prod2.csv`
and `solute_prod2.nc` sat beside a `cMD.log` describing only segment 2. The half of the directory
this package named was safe; the half the caller named was not, and the two halves look alike.

`stage_artifact_name` applies `info_csv_name`'s rule to all four: `cMD.log` at segment 1,
`cMD_prod2.log` past one, and never a segment on a stage that runs once per chain. An explicitly
passed path still wins — this changes the default, not the override.

## A remedy message named flags the command in hand does not define

`0.5.1` fixed messages that told an `md-run` user to `pass --force`, and added a test to keep them
fixed. The test scanned a list of files on the `md-run` path and that list omitted
`remd/executor.py`, which `md-run` dispatches into; and its pattern captured only the first flag
after the word "pass", so a sentence offering three remedies had one of them checked.

Both are widened, and together they found a live instance: *"Pass `--resume` to continue that run,
`--extend N` to lengthen it, or `--force` to replace it deliberately"* — where `md-run` defines
neither `--extend` nor `--force`. The imperative now names only the flag both commands have, and
the rest are described and attributed to the command that has them.

## A ladder can carry torsion restraints

hpREST2 runs a REST2 ladder with restraints on every rung, and this engine refused the combination:
`umbrella.file` was accepted only with `protocol: umbrella`, and nothing in `remd/` had ever seen a
restraint. (It has no `nmropt`/DISANG surface either; restraints are declared in this package's own
`umbrella.yaml`, against named collective variables.)

`umbrella.file` is now accepted with `REST2` and `rREST2`, and means **the same restraints on every
rung**. They are resolved by the preflight against `collective_variables.file` — before `-odir`
exists, so a selector that does not resolve refuses nothing-written — and added inside
`build_rung_systems`, the one function the driver, the preflight and the exporter all build rungs
through, **after** each rung is scaled.

**Why after, and why identical.** The exchange criterion installs a configuration in a rung's own
Context and reads its potential energy, so a bias present identically on both rungs enters `u_i`
and `u_j` alike and cancels from `log alpha` exactly; the ladder samples the restrained ensemble
with the acceptance probability it would have had unbiased. A restraint scaled by tau, or one that
differed between rungs, would enter the acceptance probability and tilt the ladder towards whichever
rung restrains least — silently, with every output still well formed. Per-rung variation is
therefore not offered rather than left to a configuration to get right.

Each restraint's force constant rides on its own per-torsion `scale`, so one definition may mix
strengths and both forms; the force's global parameter defaults to 1.0, so a rung is biased from
its first step with no runtime call. `restart.json` records the definition file and every resolved
restraint — the four atoms, the centre, the constant — under
`scientific_identity.torsion_restraints`, because `_protocol.py` can only carry the path and a
record naming a file beside an empty list understates a biased run. `export-reference` refuses such
a ladder by name: a bundle's `verify_rungs.py` rebuilds rung *i* from rung 0 by scaling, and a
restraint is not part of what that reconstructs.

Tested by arithmetic rather than by sampling: `log alpha` computed with and without the bias at the
same configurations, equal to 1e-6 kJ/mol, plus a counter-example where one rung is restrained
differently and the difference is not zero. Note what is NOT true, because it is the obvious thing
to expect: a restrained and an unrestrained ladder from one seed do not accept the same exchanges —
the bias changes the forces, so the trajectories diverge from the first propagation.

## Nothing else changes

No behaviour of a run that was already working is altered. The three fixes are: a conditional
requirement that was unconditional, four defaults that were segment-blind, and a message that
named the wrong command's flags.
