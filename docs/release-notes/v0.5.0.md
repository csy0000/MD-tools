## What MD-tools is now

One executable, `md-openmm`, and four public commands:

```text
md-openmm build-top        a structure        -> built.xml + built.pdb + built.log
md-openmm build-md         a protocol config  -> run scripts, .in files and run.sh
md-openmm md-run           an Amber-like .in  -> a stage, a ladder, or AIS switching paths
md-openmm data-register    a finished tree    -> a verified dataset under $MD_DATA
```

AIS is a `build-md` protocol and an `md-run` input, not a command of its own; `md-run` is a
subcommand, not a second executable. There is one dataset contract (v2), one configuration layout,
and one small set of documentation.

## Configuration is browsable

The repository root held a `mode-120000` symlink, so GitHub rendered `configs` as a symlink blob.
It is now an ordinary tree, with exactly one copy of each file:

```text
configs/machine/user.config.example
configs/sys/build-top.config
configs/md/{cMD,REST2,rREST2,AIS}.config
```

They ship as **wheel data files** under `<prefix>/share/md-tools/configs/`, and
`md_tools.configs.example_root()` asks the installed distribution's own metadata where they went.
No symlink, no package-data mirror, no second hand-edited copy.

The examples are no longer generated from the schemas. The guarantee that replaced byte-equality is
stronger: **every example resolves, through the real resolver, to the model's own defaults.** An
example can be reworded freely; it cannot describe a default the code does not apply.

## AIS through `build-md`

`protocol: AIS` in the same strict resolver as cMD, REST2 and rREST2.

* **tau is the only public, persisted coordinate.** `s` and `sqrt(s)` are derived inside the
  scaler and are no longer written to the observation table — a second stored coordinate is a
  second thing that can disagree with the first.
* **Every length is an exact integer step count.** `switching_duration_ps` became
  `switching_steps` and `observation_interval_steps`; logs derive ps for the reader. Three
  divisibility rules are enforced, each refused with the arithmetic that would fix it.
* Both endpoints are included, and the schedule states that **observation 0 precedes all work**:
  it is the source configuration before any parameter change and before any propagation, so its
  cumulative work is exactly zero rather than nearly zero.
* Unchanged: the work convention `ΔW_j = U(τ_{j+1}, x_j) − U(τ_j, x_j)`, fixed volume with a
  barostat refused, independent per-path seeds, completed paths never appended to, and outputs
  validated before completion is declared.
* AIS is **not** part of the cMD stage chain. It consumes an ensemble that already exists, so
  `run.sh` takes the source as a required third argument and refuses without it.

## Contract v2

| | v1 | v2 |
|---|---|---|
| canonical path | `{namespace}/{yyyy-mm}/{dataset_name}` | `{year}/{project_name}/{data_name}` |
| shared datasets | reserved `baseline/` namespace | `{year}/common/{project}/{data}` |
| dated segment | creation **month** | completion **year**, checked against the records |
| extensions | operational record | ported, **plus a required checkpoint digest** |

v2 is a new model, not a widened v1: one model accepting both shapes is the state in which a wrong
path goes undetected. A v1 manifest fails on `schema_version`, naming the difference.

**Extensions.** Completed and archived datasets are immutable; extending one creates a new dataset
with a new id that records the parent and component; new output goes to a component the new dataset
owns, never a link into the parent; lengths are mutually consistent; status and timestamps are
ordered; a completed extension cannot finish after the dataset containing it was declared complete.

v2 additionally requires `source_checkpoint_sha256`, and `source_checkpoint_copied` for an in-place
extension — which writes into the very component it restarted from, so the run can overwrite its
own restart point. Without the copy the join stops being reproducible the moment the continuation
passes it, and nothing in the record would show that it had.

Registration validates the record, cross-checks it against `dataset.yaml`, and re-hashes the
restart checkpoint if it travelled with the data. **It never opens the parent.**

`schemas/dataset-v2.0.schema.json` and `schemas/extension-v2.0.schema.json` are generated from
their pydantic models and drift-checked by tests.

## One release blocker found and fixed

`.gitignore` carried a bare `build/` rule for Python artifacts. A bare pattern matches a directory
of that name at **any** depth, so it also matched `src/md_tools/build/` — the package implementing
`build-top` and `build-md`.

Those five modules had never been committed. They were absent from `origin/dev` and from the
preservation tag; a clone of this repository did not contain two of the three commands the project
exists to provide. Everything passed locally because the files were on the machine that wrote them.

Fixed by anchoring the rules (`/build/`, `/dist/`, `/data/`, `/logs/`) and committing the modules.
A test in `test_suite_integrity.py` now walks `src/`, `tests/` and `configs/` and fails if
`git check-ignore` matches any source file. Verified by cloning `dev` and building a working wheel
from the clone.

## CI

`.github/workflows/release.yml` was not evidence for this package: it invoked `show-default`,
`sys-config`, `sys-gen` and `md-gen`, none of which exist. It is replaced by
`.github/workflows/ci.yml`, which runs on pull requests, on pushes to `dev` and `main`, and on
manual dispatch — so it speaks for the branch under review rather than only for a tag. Tag-driven
validation moves to `v*`; `openmm-v*` named this package under its former name.

The job builds the wheel, installs it with no source tree importable, and then runs every
interface check from a directory outside the checkout — proven, not assumed, by asserting
`md_tools` resolves inside `site-packages`. It validates the four commands, refuses the retired
ones, locates and resolves the shipped examples through distribution metadata, generates every
protocol and compiles what is written, compares both exported schemas against their models, and
runs the non-GPU lane with a skip treated as a failure.

Two `md-run` checks were added to it, both of which a runner with no GPU can make: `md-run -h`
must answer and document every documented flag, and `-ng` outside an MPI launch must be refused.
Neither needs a device, and both are exactly the kind of thing that breaks silently.

It runs **no dynamics** and says so in a job notice. There is no CUDA runner; the GPU lane is
local and is the table below.

**Its first run failed, and finding that was the point.** Run `33523698117` on `dev`: every
packaging and interface step passed on a real runner — the wheel, the commands, the refused
subcommands, the shipped examples, all six bundles, both schemas — and the test lane failed on 8
skips. `cpptraj` and Amber's reference `rem.log` were being read from absolute paths under one
workstation's software tree, so the only tests that check our Amber trajectory and H-REMD log
against the real parser had been skipping on every machine but that one, while the suite reported
success. AmberTools is installed on the runner; the paths simply did not exist there.

Fixed by finding `cpptraj` on `PATH` and vendoring the 3.6 KB Amber reference into `tests/data/`,
and `test_no_test_hard_codes_a_path_on_one_machine` now fails if a test locates anything through
`/home`, `/data*`, `/scratch` or `/Users`. The guard was verified against the original defect
rather than assumed to work.

Run `33551381960` is **green**: 664 passed, 0 skipped, in 1 m 42 s — the same count this machine
gets, which is the point. Those eight tests now run on the runner instead of reporting success
without having executed.

## A stable import API, and generated files that are entry points

The behaviour used to live in the generated files. That made every generated directory a *copy*:
fixing a defect meant regenerating every project ever produced, and two directories generated a
month apart ran different code while claiming the same protocol.

```python
#!/usr/bin/env python
from md_tools.md import run_generated_stage
raise SystemExit(run_generated_stage(__file__, "min"))
```

Twelve lines including the docstring, and the same shape for `md.py`, `REST2.py`, `rREST2.py` and
`AIS.py`. `resolved.config` beside the script is the single resolved declaration -- located from
`__file__` so a directory can be moved, re-validated by the strict resolver at execution, and bound
into the checkpoint fingerprint by digest.

| package | exports |
|---|---|
| `md_tools.md` | `PositionalRestraint`, `ReportingConfig`, `run_stage`, `run_generated_stage`, `run_generated_workflow` |
| `md_tools.rest2` | `REST2Scaler`, `ScalingSelection` |

| `md_tools.remd.reservoir` | `ReservoirRefreshRule` |

### The bare-import mechanism, and what it was hiding

Those modules imported each other by bare name, which resolved only because the runtime put their
directory on `sys.path`. While it was there, **`remd/statistics.py` shadowed the standard library's
`statistics`** for anything that imported it — `pytorch_lightning` failed with
`module 'statistics' has no attribute 'mean'` during this migration, which is how it was found.

There is now no `sys.path` insertion anywhere in `src/`, and a test asserts it stays that way.

### rREST2 composes rather than forks

`REST2Scaler` + `REMDRunner` + `NeighborExchangeRule` + `ReservoirRefreshRule`. The reservoir rule
is generic and lives in `md_tools.remd.reservoir` rather than in a file named after its first user,
so a future reservoir REMD method reuses it instead of copying the driver again.

The exchange mathematics that was duplicated between `rest2_scaling.py` and `replica_engine.py` is
now in one place, after the two were verified bit-identical over 2000 random inputs.

### One implementation of each low-level operation

The migration claimed this and did not have it. A check afterwards found `sha256_file` defined in
**four** modules, `derive_seed` in three, and `resolve_platform` in two.

`sha256_file` is now only in `build/record.py` — all four produced identical digests, which is
precisely why nobody noticed there were four. It lives there because hashing a file needs no
OpenMM and that module is the lowest-level of the four.

The other two are **different operations that shared a name**, which is a worse problem than a
duplicate, and they are renamed rather than merged:

* `openmm.seeds.derive_seed` → `derive_build_seed`. A SHA-256 used while a System is built. The
  run-time `md_tools.md.derive_seed` is the repository's older multiplicative hash and *cannot* be
  changed to match it: AIS selects its starting frames from it, so a different derivation would
  silently change which configurations every existing AIS project starts from.
* `remd.engine.resolve_platform` → `build_platform`. It constructs a `Platform` from a name
  already decided. `md_tools.md.resolve_platform` decides the name and **refuses a CPU fallback**,
  because a silent fallback still finishes, still writes a trajectory and still says complete.

**A difference worth knowing about, since resolved.** Those two platform policies were not the
same: a ladder given no explicit platform, on a machine with no visible CUDA device, ran on the
CPU — where a stage would refuse. It was recorded in the run context, so such a run was never
invisible, but it was not refused, and tightening it was a behaviour change that needed its own
validation.

That validation was done in the `md-run` work. There is now ONE resolver,
`md_tools.openmm.platform_policy.resolve_platform_request`, and stages, ladders and AIS all go
through it: **CUDA unless `--cpu`, with no fallback anywhere.** Listing the CUDA platform is not
the same as having a usable device — conda-forge ships the plugin unconditionally — so the
resolver opens and discards a one-particle Context to prove it, which puts the failure before a
minimisation rather than after one. The record carries `requested_policy`, `explicit-cpu` or
`default-cuda`, so a CPU result can never be mistaken for an unnoticed fallback.

## `md-openmm md-run`: the Amber-like execution interface

Four subcommands now -- `build-top`, `build-md`, `md-run`, `data-register` -- and still exactly one
executable. `pyproject.toml` installs one console script and a test asserts it.

```bash
md-openmm md-run -i min.in -p built.pdb -s built.xml -r min.xml -log min.log
mpirun -n 8 md-openmm md-run -ng 8 -i REST2.in -p built.pdb -s built.xml -odir REST2/
mpirun -n 8 md-openmm md-run -ng 8 -i AIS.in  -p built.pdb -s built.xml \
          -source-traj hot/cMD.dcd -odir AIS/
```

`md-run` is a **surface**, not a second implementation. Each protocol is handed to the same
function a generated script calls -- `stage_main`, `replica_main`, `ais_main` -- so nothing is
reachable from one and not the other.

`build-md` now writes an `.in` beside each `.py`, and `run.sh` drives `md-openmm md-run` rather
than `python <stage>.py`, because that is the interface a person types. Every generated `.in`
resolves to exactly the `resolved.config` beside it; that round-trip is asserted for all four
protocols and every generated input. **`resolved.config` is authoritative** -- md-run writes it
into `-odir` with the `.in` file's sha256, so the chain from what a person wrote to what ran is a
link rather than a claim.

### What running it on real hardware found

Five defects, none of which any suite could see, all found the first time the four tiers were
actually launched on this machine's nine GPUs:

| defect | consequence |
|---|---|
| md-run dispatched on protocol, not stage | `min.in` of a REST2 workflow went to the replica executor, which had no coordinates |

### The input files, and which one is authoritative

`build-md` now writes an `.in` beside each `.py`, and `run.sh` drives `md-openmm md-run` rather
than `python <stage>.py` -- that is the interface a person types, and a script using a different
one is a second way to run the same thing that can drift from the documented way.

**`resolved.config` is authoritative.** md-run writes it into `-odir` before anything integrates,
with the `.in` file's sha256 in its header, so the chain from what a person wrote to what ran is a
link rather than a claim. Editing `resolved.config` between a run and its continuation changes the
fingerprint and the continuation is refused; editing the `.in` afterwards changes nothing at all
and its recorded digest simply stops matching, which is how you find out. A `-odir` that already
holds a *different* `resolved.config` is refused rather than overwritten.

Every generated `.in` resolves back to exactly the `resolved.config` beside it. That round-trip is
asserted for all four protocols and every generated input, and it found two defects that would
otherwise have made an input mean something else:

* floats written with `%g`: `300.0` became `300` and read back as an integer;
* keys matched by reconstructing their target from their name, which silently dropped every input
  deliberately spelled differently from the field it sets -- `random_seed` -> `dynamics.seed`,
  `reservoir_enabled` -> `reservoir.enabled`.

A third was found only by a CUDA smoke test whose configuration set `dynamics.platform`: the input
language could not express that field at all, so it was dropped between the `.in` and the
`resolved.config` it came from. The check is now over the MODEL -- every field of every resolved
block must be writable in an `.in` file -- rather than over whichever example a test happened to
use.

## Six corrections to the `md-run` surface

Review of the `md-run` work found six contracts that were wrong rather than incomplete. Each is a
promise the code made and did not keep, so each is corrected here with a regression test written
first.

### 1. The short flags are Amber's

**This supersedes the mapping in which `-x` named `built.xml`.**

```bash
md-openmm md-run -i min.in -p built.pdb -s built.xml -c prev.xml \
          -o min.out -x min.dcd -r min.xml -log min.log
```

| flag | meaning | Amber |
|---|---|---|
| `-i` | run input | mdin |
| `-o` | human-readable simulation output | mdout |
| `-p` | topology / reference PDB | prmtop |
| `-c` | input restart | inpcrd / restrt |
| `-r` | output restart | restrt |
| `-x` | output trajectory | mdcrd |
| `-s` | serialised OpenMM System | — |

`-x` has meant mdcrd for decades. Using it for the System here trained people to type the one
command that would write a trajectory over the System their run needs, so both mistakes are refused
by name: a `.dcd` in `-s`, an `.xml` in `-x`, and the two resolving to one path. `-s` is required;
`-x` is optional, defaulting to `<stage>.dcd`, and is refused for AIS, which writes one trajectory
per path that no single name could describe. `allow_abbrev=False`: `--traj` errors instead of
quietly becoming `--trajectory`.

### 2. `-o` and `-log` are two files

They were aliased, on the argument that this package writes one readable record. That conflated two
audiences and made a person open a machine record and scroll past a hundred lines of hashes to see
whether a simulation was moving.

`.out` is a running account — stage, settings, a progress table of step, time, potential, kinetic
and total energy, temperature, volume, density and speed, then how it ended. Line-buffered, so
`tail -f` works. `.log` is unchanged: the provenance record `read_record` parses. Each names the
other, they default to `<name>.out` and `<name>.log`, and only a genuine collision is refused.

### 3. The platform is a property of the machine

`dynamics.platform` is gone from the scientific schema, from every shipped protocol config and from
the `.in` language. It is now:

```yaml
machine:
  openmm:
    platform: CUDA        # or CPU, for a deliberate machine-wide default
    precision: mixed
    device_policy: local_rank
```

in the user configuration, found through the discovery order that already existed and defaulting to
CUDA / mixed / local_rank when the file or the block is absent. `data-register --init` writes it
out. A configuration written before the block existed is still valid. `dynamics.platform` is
refused with this migration rather than an unknown-key suggestion: the key was not misspelled, it
moved, and a protocol config that carried it carried one machine's hardware into every repository
it was shared through.

`--platform` is gone from `md-run`; a per-run platform flag would be a second authority for a
machine property. `--cpu` is the one override, `--device` says which GPU and never whether, and the
two are refused together. The record now distinguishes the three ways a platform can be chosen,
because a CPU result has three possible causes and only one of them is nobody's decision:
`built-in default`, `machine.openmm`, `--cpu (command line)`. It also carries the CUDA driver
version alongside the OpenMM version.

### 4. Every accepted AIS reporting option now does something

`reporting.system_printout` and `reporting.checkpoint_printout` were validated and then dropped.
The runtime never saw the `reporting` block at all, so both were accepted, consequential-looking
and inert — the one thing a strict input language must never be.

Four independent cadences, each dividing `switching_steps` on its own:

| setting | controls |
|---|---|
| `ais.observation_interval_steps` | work observations — this one is the method |
| `reporting.solute_printout` | frames in `AIS_trajNNNN.nc` |
| `reporting.system_printout` | `path_NNNN/system.csv`: potential, kinetic and total energy, temperature, volume, density |
| `reporting.checkpoint_printout` | how often the path becomes resumable |

The rule forcing `solute_printout == observation_interval_steps` is gone. It answered "how often is
a configuration written" with the answer to "how often is work measured", and work every 10 steps
with frames every 50 is an ordinary thing to want.

A density bug the state table exposed immediately: the dalton-per-nm³ to g/mL factor was
1.66053906660 where it should be 1.66053906660e-3, so TIP3P water came out at 947 g/mL. Wrong by
1000, and it looks like a number rather than a mistake — which is why the constant is now written
as the ratio it is, with the arithmetic in a comment.

### 5. Exact mid-path resume

An OpenMM binary checkpoint plus a sidecar holding everything outside the Context: accumulated
work, work since the last observation, and how many work rows, frames and state rows are on disk.
Restoring one without the other resumes a simulation into somebody else's bookkeeping.

On `--resume`, every fingerprint — System, topology, source ensemble, schedule, path id, source
frame, seeds — is checked **before anything loads**, then the streams are cut back to the counts
the sidecar vouches for, so a record interrupted mid-write is dropped rather than appended to.

mdtraj's NetCDF writer offers `r` and `w` and no append, and that turned out to be the right
constraint: a frame interrupted mid-write reads as present without being complete, so appending
onto an unverified tail would be wrong even where the format allowed it. A resume rewrites the
vouched-for frames into a fresh file and continues. Frames are staged inside the path directory and
published to `AIS_trajNNNN.nc` in one atomic move after validation — until then nothing at the run
root could be mistaken for a finished path. A completed path is skipped, and its checkpoint is
deleted so nothing invites a resume of finished work.

### 6. MPI fails closed

`barrier()` caught `ImportError` and returned. `mpirun -n 8` on a machine without a working
`mpi4py` therefore ran eight processes that never met: eight independent simulations writing over
one set of output paths, each believing it was the whole ladder, and the result looked complete.

`md_tools.remd.mpi` imports `mpi4py`, requires MPI initialised and not finalised, and compares the
launcher's rank and size against the communicator's and both against `-ng` and the replica count —
all before an output directory, `resolved.config`, log or Context exists. A mismatch names all four
numbers, because naming the two that differ leaves the reader to work out which of the others to
change. Serial is untouched: world size 1 imports nothing and a no-op barrier is correct when there
is genuinely nobody to wait for. `mpi4py` is an extra (`pip install md-tools[mpi]`), and its
absence is never a silent downgrade.

### Genuine formats

`md_tools.openmm.trajectory` decides what a file IS from its leading bytes — `CORD` at offset 4 for
DCD, `CDF\x01` or the HDF5 signature for NetCDF — never from its suffix.

* ordinary MD writes DCD through OpenMM's native reporter, and refuses a `.nc` trajectory name:
  OpenMM has no native NetCDF writer, and renaming a DCD does not convert it;
* AIS accepts a genuine DCD (the ordinary fixed-τ cMD source) or a genuine NetCDF, and refuses one
  whose suffix and contents disagree, naming both;
* AIS and REST2 outputs stay genuine NetCDF, and the tests open them with mdtraj rather than
  trusting the extension.

## Corrective round: preflight, MPI, configuration and restart

Review of `1e2e5b9` found six contracts that were wrong rather than incomplete. The theme is that a
safe outer wrapper was hiding an unsafe runtime.

### One MPI authority

Two permissive implementations survived outside `md_tools.remd.mpi` -- `executor.barrier` and
`driver.Coordinator` -- both spelling:

```python
try:
    from mpi4py import MPI
except ImportError:
    return
```

which is true of a serial run and false of every other kind. Under `mpirun -n 8` with a broken
mpi4py they produced eight processes each believing it was the only one, all eight driving every
state, all eight writing the same files. The failure is invisible precisely because it only occurs
when MPI is broken.

`Coordinator` is now a subclass of the one `Coordination` and adds nothing; `barrier` delegates. A
test walks the AST of every module in the package and fails if `mpi4py` is imported anywhere else
-- the AST rather than the text, so a docstring that quotes the retired code to explain it is not
mistaken for the code.

`Coordination.fail` makes a rank-local error collective: it prints the reason from the rank that
has it and calls `Abort`, so a multi-rank failure is a stopped job rather than a hung one. A rank
that raises alone leaves the others blocked in the next collective until a scheduler kills them.

### The guard is in the runtime, not the wrapper

`replica_main` and `ais_main` validate the LAUNCH themselves, before `-odir` exists, because the
generated `REST2.py`, `rREST2.py` and `AIS.py` call them directly. A guard that lives only in
`md-openmm md-run` is a property of one entry point, and a safe wrapper over an unsafe runtime is
worse than no wrapper: it makes the unsafe path look tested. AIS gained `-ng`, checked against the
communicator.

**This round covered the MPI launch and not the rest of the preflight, and the claim below was
broader than the tests supported.** A generated script still created its output directory, its
`.out`, its `.log`, `solute.yaml`, `_protocol.py` and a group file before discovering that the
machine configuration was malformed or that CUDA could not open a Context. That is corrected in
"Preflight, shared by the dispatcher and the direct runtimes" further down, where the coverage is
stated against the tests that demonstrate it.

### Preflight before any output

`md_tools.run.preflight` runs every check -- flag roles, resolved-path collisions, input existence,
source format, the MPI launch, the machine configuration, `--cpu`/`--device`, the device policy,
platform availability, and a real CUDA Context -- before `-odir`, `resolved.config`, the `.out`,
the `.log`, a group file, a trajectory or a checkpoint exists. `md_run_main` previously wrote
`resolved.config` first, so a refused run left a directory that reads as a run which happened.

Collisions compare RESOLVED paths, so `-o sub/../run.out` and `-log ./run.out` are recognised as
one file; string comparison missed that and one would have truncated the other.

### Absent configuration is not invalid configuration

`machine_openmm_settings` caught every `RegistrationError` and answered with the built-in defaults.
Bad YAML, a duplicate key, an unknown field, an invalid platform -- all became
CUDA/mixed/local_rank, so the machine ran on settings nobody chose and the file that said otherwise
was never mentioned again.

A genuinely absent file still resolves to the defaults. An existing broken one is fatal, read
through the strict duplicate-rejecting loader, and every refusal names the file.
`MD_TOOLS_CONFIG` naming a missing file is a broken reference rather than an absence: somebody
meant that path, and defaults would hide the typo.

### Truthful provenance, and a device policy that does something

`machine.openmm.platform: CPU` was recorded as `explicit-cpu`, indistinguishable from a per-run
`--cpu`. The record now carries `platform_selection` (`built-in-default` | `machine-config` |
`cli-override`) and `cli_cpu_override` separately.

`device_policy: openmm` was accepted by validation and never consulted -- AIS chose a local-rank
device before the machine setting was read. The policy is now read first, and both values do what
they say: `local_rank` assigns one rank per visible device, `openmm` sets no `DeviceIndex` and lets
OpenMM choose. A configuration field with no runtime effect is worse than an absent one, because
somebody set it and believes it took hold.

### Crash-atomic AIS checkpoints

The previous commit overwrote the binary checkpoint and then replaced the sidecar. Atomic
replacement of the sidecar does not make the PAIR atomic: a crash in between left a new Context
checkpoint beside old accumulated work, and resuming that continues from step 3000 while believing
it is at step 2000. It re-emits rows that exist and reports the work of a path nobody ran. Nothing
fails.

`md_tools.ais.checkpoint` is a generation transaction:

```text
path_0000/checkpoints/generation_000013.chk   written to a NEW name, fsynced, digested
path_0000/checkpoints/generation_000013.json  the sidecar, carrying that digest, fsynced
path_0000/current_checkpoint.json             replaced atomically, LAST
```

A crash before the pointer lands leaves the previous generation committed; a crash after it leaves
a pointer whose files were already durable. Resume follows only the pointer and verifies the
checkpoint's sha256 before loading -- never "the newest generation", because the newest file is
exactly what a crash leaves behind.

`tests/test_checkpoint_transaction.py` injects a crash at each of the five boundaries, twice: once
with a previous generation committed and once without, and asserts what `read_committed` returns
in every case.

## Preflight, shared by the dispatcher and the direct runtimes

The previous round put a shared preflight behind `md-openmm md-run` and described the direct
runtimes as covered. Only the MPI launch was. Everything else -- the machine configuration, the
platform, path collisions, input existence, topology/System agreement -- was still checked after
`stage_main`, `replica_main` and `ais_main` had begun writing. A generated `min.py` opened its
`.out` and `.log` at line 212 and read the machine configuration at line 325.

`md_tools.run.preflight` is now mode-aware and CONSUMED, not merely called:

```python
preflight_stage(...)  -> StagePreflight     # split stages and all-in-one workflows
preflight_ladder(...) -> LadderPreflight    # REST2 and rREST2
preflight_ais(...)    -> AISPreflight       # switching paths
```

Typed results rather than one dictionary with optional keys: a `coordination` that is sometimes
None-meaning-serial and sometimes None-meaning-unchecked is a value whose meaning depends on who
is reading it, and the reader who gets it wrong is the one running eight ranks over one set of
files. Each runtime then USES the result -- `checked.acceleration`, `checked.coordination`,
`checked.record()` -- rather than resolving the platform, the machine settings or the MPI world a
second time. `stage_main` and `ais_main` each had their own copy of that resolution; both are
gone.

Two duplicate policies were removed with them: `stage_main` compared `-o` against `-log` on its
own (missing `-x`, `-r` and `-chk`, and firing before the shared check, so the message depended on
which implementation reached the case first), and checked the trajectory suffix separately.

The all-in-one workflow validates the WHOLE chain before its first stage writes anything. Per-stage
preflight could not have caught a broken configuration until stage four, with three stages of
output already on disk.

`stage_parser` and the workflow parser gained `-odir`, `-o` and `--cpu`, so a stage run directly
takes the same flags as one run through `md-openmm md-run`.

## AIS recovery, through the real path runner

`tests/test_checkpoint_transaction.py` proves the commit is atomic. That is necessary and not
sufficient: recovery has to reconcile four things written by different code at different moments --
trajectory frames, work rows, state rows, and the committed sidecar's counters.

`tests/test_ais_recovery_integration.py` drives `run_one_path` itself over a real four-particle
OpenMM Simulation on the Reference platform. Not a mock: every object the runner touches is the
real type, so `saveCheckpoint`, `loadCheckpoint` and `XmlSerializer` exercise production code. What
is small is the system, not the fidelity.

Eleven fault boundaries, each armed to fire after a generation is already committed:

* the five commit boundaries (`after-checkpoint-write` … `after-pointer-replace`);
* six stream boundaries -- before and after a frame, a work row and a state row becomes durable.

After each, the resumed path is asserted to finish with exactly the counts an uninterrupted run
produces, on the same step grid with no duplicates, with the cumulative work still the running sum
of its increments across the boundary, and the same source frame. **The committed counters are the
authority**: a frame that reached the disk after the last commit is dropped and rewritten, never
kept because the file happened to be longer.

Also asserted: an uncommitted newer generation is ignored by the runner; a corrupt committed pair
is refused with a message that says which directory to delete and that the other paths survive; a
completed path clears its transaction and a later `--resume` leaves its trajectory byte-identical;
and a sidecar whose fingerprint names a different run is refused before anything loads.

## Remaining

Recorded rather than hidden.

**The instruction's own file count.** It asks for "all seven" configuration examples while the
tree it draws enumerates six. The tree is the specification and six is what ships; the test asserts
the exact set rather than any count, so it fails both on a missing file and on an undeclared one.

**The ladder's default process model.** Run without `mpirun`, a ladder is a single process holding
every state and letting OpenMM choose the device. This is correct and is what the older smoke test
exercises. A real multi-process ladder is now in the automated lane too:
`tests/test_md_run_mpi_gpu.py` runs a two-rank ladder under `mpirun`, asserts one trajectory per
fixed state and no third, and asserts that each rank recorded WHICH device it took and by what
rule.

**AIS results are not bit-identical across worker counts, and cannot be.** Path IDENTITY is:
`paths_for_rank` is a pure function, so path *n* starts from the same source frame with the same
seeds and writes `AIS_traj000n.nc` whatever the world size, and that was checked at 1 and 3
workers over 12 paths. The work VALUES differ by up to 0.53 kJ/mol against a 4.16 kJ/mol spread
across paths -- CUDA mixed-precision reduction order, amplified along 500 steps of a chaotic
trajectory. That is a property of the hardware, not of the scheduling, and no amount of care in
the distribution would remove it.

**Work values are not bit-reproducible; path identity is.** Restated here because the corrections
did not change it. `paths_for_rank` is a pure function, so path *n* starts from the same source
frame with the same seeds and writes `AIS_traj000n.nc` whatever the worker count. The VALUES differ
by CUDA's reduction order, amplified along a chaotic trajectory.

**A stage cannot be resumed across platforms.** An OpenMM binary checkpoint belongs to the platform
that wrote it. That is OpenMM's constraint, not something this package can work around; what
changed is that it now says so in those words instead of surfacing as an internal-looking
exception.

**`ais.tau_start` is asserted, never verified.** Nothing in a coordinate trajectory records the
Hamiltonian it was sampled under. The log says so and records `tau_verified_from_file: false`. The
AIS method page had claimed the opposite -- that the source's own record was checked against
`ais.tau_start` -- and that claim is corrected.

**One deliberate deviation from the instruction.** Its example AIS input writes
`source_frame_selection = random`. That is refused, with `uniform_random` named in the message.
Accepting both would give one concept two spellings, which is the rule the rest of the parser is
built on -- a configuration language with several spellings for one value has several ways to typo
it. Every other key in that example parses, and each is asserted to reach the field it sets.

**`tau_start` is asserted, never verified.** Nothing in a coordinate trajectory records the
Hamiltonian it was sampled under, so an AIS run cannot check that its source really is at
`tau_start`. The log says so in those words, and records the assertion as
`tau_verified_from_file: false`, so a reader checks it against the run that produced the file
rather than assuming it was checked here.

**An AIS resume is not bitwise reproducible, and is not asserted to be.** The resumed path
produces the same number of work rows, frames and state rows at the same protocol steps, with the
same source frame, seeds and filename, and a cumulative work that is still the running sum of its
increments across the boundary. The VALUES differ from an uninterrupted run: the Context restarts
from a checkpoint, and CUDA's reduction order is not fixed. Requiring bitwise equality would be
requiring something the hardware does not offer.

**A rank-local abort is `MPI_Abort`, which is abrupt by design.** Ranks that were mid-write when
another rank failed leave whatever the filesystem had. That is the correct trade -- the
alternative is a job that hangs in a collective until a scheduler kills it -- and it is why a
path publishes its trajectory only after it is complete and validated, so an abrupt end leaves
nothing that reads as finished work.

**Not done here, by instruction.** `dev` is not merged to `main`, nothing is published to PyPI,
no `v0.5.0` tag exists, and the version remains `0.5.0.dev0`. This is a release candidate for
review, not a release.

## The AIS tau-basis decomposition

### Why

A switching path recorded one number per update: the total work. Reweighting that nonequilibrium
ensemble onto a *different* Hamiltonian — a different tau schedule, a different endpoint, or a
Hummer–Szabo estimator evaluated at a tau the path never visited — needs the potential as a
**function** of tau. A total at the one tau that was run does not contain that function, and
re-running the path at another tau is not reweighting.

### The identity

Write the coupling amplitude as `a = 1 − τ`. Every scale factor in this REST2 convention is a
power of it:

| group | factor | terms |
|---|---|---|
| unscaled | `a⁰` | bonds, angles, excluded omega torsions, environment–environment nonbonded |
| linear | `a¹` | solute–environment nonbonded, the whole generalized-Born energy |
| quadratic | `a²` | solute–solute nonbonded and 1–4, eligible solute torsions, solute CMAP |

so at **frozen coordinates** the potential is exactly a quadratic polynomial in `a`:

```
U(τ, x) = U_unscaled(x) + a·U_linear(x) + a²·U_quadratic(x)
```

This is an identity, not a model, and it holds for the whole `NonbondedForce` — **including the
PME reciprocal sum, the Ewald self-energy and the long-range dispersion correction**. Each of
those is a quadratic form in the per-particle charge (or in `sqrt(ε)`), and the scaler multiplies
solute charges by `a` and solute epsilons by `a²`, so a pair term carries
`a^(number of solute partners)`. Nothing is decomposed per pair, and the validated force
construction is untouched.

### How it is measured

Three potential-energy evaluations per switching update, at controlled amplitudes `a ∈ {0, ½, 1}`,
at frozen coordinates, then one exact quadratic through them. Three points determine a quadratic,
so the fit contributes no model error: the only error is the floating-point error of the three
evaluations. The nodes are as far apart as the domain allows, because the fit divides by their
differences; `a = 0` switches every scaled term off and therefore reads `U_unscaled` directly
rather than inferring it.

`τ = 1` is not a legal protocol coordinate and `scaling_for_tau` still refuses it. The probe goes
through `scaling_for_amplitude` and `TauSwitcher.set_amplitude`, which is the same restore-and-
rescale code a real switch uses — a separate probe implementation would be a second Hamiltonian,
agreeing with the first only until one of them was edited.

> **Superseded below.** The section that follows describes the FIRST version of this output, in
> which the potential columns carried the pre-switch work basis under names that read as
> potentials at the row's saved frame. That is scientifically wrong for reweighting and is
> corrected in "The frame-aligned Hummer–Szabo correction" at the end of this document. It is left
> here because a reader holding a v1 file needs to know what its columns meant.

### Columns (schema v1 — superseded)

Twelve, appended to every per-path observation row and to `AIS_work.csv` (never inserted among the
existing ones, so a reader keyed on position keeps reading the same numbers):

```
potential_unscaled_kj_mol              potential_linear_basis_kj_mol
potential_quadratic_basis_kj_mol       potential_linear_contribution_kj_mol
potential_quadratic_contribution_kj_mol potential_total_reconstructed_kj_mol
delta_work_unscaled_kj_mol             delta_work_linear_kj_mol
delta_work_quadratic_kj_mol            total_work_unscaled_kj_mol
total_work_linear_kj_mol               total_work_quadratic_kj_mol
```

The **basis** values are tau-independent and are what a reweighting reads; the **contributions**
are those values as they enter `U` at that row's tau. Both are written, because deriving one from
the other needs the convention, and a column that needs a convention to read is a column that gets
read wrongly. Component totals and the schema identity also go to `AIS_paths.csv`, the checkpoint
state, the completion manifest and the provenance record.

Which instant a row describes: the work columns are cumulative to that protocol step; the
component **potential** columns are the frozen-coordinate measurement of the last parameter update
contributing to the row. `potential_total_reconstructed_kj_mol` is therefore exactly the
`U(τ_after, x_frozen)` whose difference from `U(τ_before, x_frozen)` is that update's total work —
which is what makes it comparable to a directly measured number rather than to nothing.

### What is checked rather than assumed

The total work is still measured directly, `U(τ_{j+1}, x_j) − U(τ_j, x_j)`, from two evaluations of
the real Hamiltonian. The components are derived independently, from the fit. The run then
**requires** them to agree:

```
ΔW_total = ΔW_unscaled + ΔW_linear + ΔW_quadratic
```

and refuses rather than recording a decomposition of a work value it cannot reproduce. Deriving
the total *from* the components would make that identity true by construction and test nothing.

`ΔW_unscaled` is exactly `0.0` and is written as the literal it is: the unscaled group has no tau
dependence and the coordinates do not move during a parameter update. The column is kept so the
zero is visible in the file rather than implied by its absence — and a nonzero value there is the
signature of a force that acquired a tau dependence the three-group model does not describe.

### Numerical tolerance

Documented per OpenMM precision, as `(relative, absolute floor)` in kJ/mol
(`md_tools.ais.decomposition.RECONSTRUCTION_TOLERANCES`):

| precision | relative | floor |
|---|---|---|
| `double` | 1e-9 | 1e-6 |
| `mixed` | 1e-6 | 1e-3 |
| `single` | 5e-5 | 1e-1 |

The reconstruction is a fixed linear combination of three energies measured on one Context, so its
error is the energies' own, amplified by the fit coefficients (magnitudes 1, 3 and 4 for these
nodes). `single` is deliberately loose: a solvated potential is order 1e5 kJ/mol and a
single-precision nonbonded sum carries roughly 1e-6 relative error, so a tighter tolerance would
report the platform's arithmetic as a defect in the decomposition.

### Cost, measured

Three extra potential-energy evaluations per switching update and **no extra integration steps**.
Recorded in provenance rather than estimated:

```yaml
decomposition:
  potential_energy_evaluations_per_update: 3
  switching_energy_evaluations: <total for this run>
  switching_energy_evaluation_seconds: <measured wall clock>
```

Measured on CUDA, at `parameter_update_interval_steps: 1`, on the two system sizes this branch
verifies (`test_the_decomposition_cost_is_measured_on_a_large_system`):

| system | particles | probe evaluations | seconds | per evaluation |
|---|---|---|---|---|
| ALA, implicit GBn2 | 22 | 63 | 0.286 | **4.55 ms** |
| ALA, explicit TIP3P | 1796 | 63 | 3.404 | **54.0 ms** |

**Read the second row before choosing an update interval.** Twelve times the cost per evaluation
on a system eighty times larger says the probe is not dominated by the energy evaluation but by
the parameter push: `updateParametersInContext` walks every particle and every exception of the
`NonbondedForce`, three times per update, plus a fourth to restore the path's own tau.

So on a solvated system the decomposition is cheap per *step* and expensive per *update*. At the
default `parameter_update_interval_steps: 1` it costs roughly 0.16 s per switching step, which for
a 500-step path is around 80 s of probing per path — comparable to the dynamics. A larger update
interval reduces it proportionally and changes the physics not at all in the components: the work
is still exact, because the identity is exact at whatever amplitudes the schedule visits. What a
larger interval changes is the switching protocol itself, which is a decision to make on its own
merits.

This is the honest number, not a favourable one. The 22-particle figure alone would have been
misleading, which is why the lane measures both.

**The identity holds through PME.** On the explicit lane the worst
`|Σ components − measured total|` over the whole work table was **4.7e-5 kJ/mol** on energies of
order 1e4, at mixed precision — which is the reciprocal sum, the Ewald self-energy and the
long-range dispersion correction all decomposing exactly as the algebra says they must. No
implicit lane can test that, because none of those terms exists in one.

### Tested

`tests/test_ais_decomposition.py` builds systems where the answer is known term by term and checks
that each lands in the group the convention names — bonds and angles wholly unscaled, GB in the
**linear** basis and not the quadratic one (which is the retired v1 Hamiltonian), 1–4 and CMAP and
eligible torsions quadratic, and an excluded omega torsion whose energy *moves* from the quadratic
group into the unscaled one while `τ = 0` is unchanged. Also the forward/reverse sign convention,
frozen-coordinate telescoping, and that a probe restores its tau even when an evaluation raises.

`tests/test_ais_recovery_integration.py` covers the accumulators across an interruption at every
transaction and stream boundary, an observation cadence wider than the update cadence, and refusal
of a checkpoint written under another basis version or under none. The identity is verified on
real CUDA in `tests/test_cuda_coverage_matrix.py::test_ais_decomposition_lane`.

### Hummer–Szabo

The three basis values are what an estimator needs to evaluate `U(τ)` at a tau the path never
visited, which is what reweighting a nonequilibrium ensemble onto another Hamiltonian requires.
**This package still computes no estimator.** The columns are the input one would consume.

## The frame-aligned Hummer–Szabo correction (schema v2)

### What was wrong

A switching update moves the parameters at frozen coordinates `x_j`, then propagates the
configuration to `x_{j+1}`. Schema v1 wrote the trajectory frame for `x_{j+1}` and, on the same
row, the potential basis measured at `x_j` — one propagation earlier — under column names that
read as potentials at that frame.

A Hummer–Szabo reweighting from such a file pairs the **work of one configuration** with the
**energy of another**. Nothing raises. Every number is plausible, every internal consistency check
passes, and the error is invisible in the output.

### Two probes, at two coordinates

| probe | coordinate | what it is for |
|---|---|---|
| **work basis** | frozen pre-switch `x_j` | decomposes the incremental and accumulated work — the right coordinate, because the convention *is* `U(τ_{j+1}, x_j) − U(τ_j, x_j)` |
| **observation potential** | the coordinate the row SAVES, `x_t`, under that row's τ | the energy basis a Hummer–Szabo reweighting consumes |

A row naming a `coordinate_frame_index` carries potentials recomputed at that frame. A row with no
saved coordinate — the cadences are independent — leaves those cells **empty by schema** rather
than borrowing a neighbour's.

### The three groups, named by their power of λ

With `a = 1 − τ` and `λ = a²`:

```
U(τ, x) = U_non_scaled(x)
        + sqrt(λ) · U_sqrt_scaled(x)          sqrt(λ) = a
        + λ       · U_lin_scaled(x)           λ = a²
```

| column | group | terms |
|---|---|---|
| `potential_non_scaled_kj_mol` | `λ⁰` | bonds, angles, excluded omega torsions, environment–environment |
| `potential_sqrt_scaled_kj_mol` | `sqrt(λ)` | solute–environment nonbonded, the whole generalized-Born energy |
| `potential_lin_scaled_kj_mol` | `λ` | solute–solute nonbonded and 1–4, eligible solute torsions, solute CMAP |
| `potential_reconstructed_kj_mol` | — | the identity above, evaluated |
| `potential_direct_kj_mol` | — | an independent `getState(getEnergy=True)` at the same coordinate and τ |

"Linear" and "quadratic" were ambiguous until you said linear in *what*; these names say it.

Both totals are written so the identity is checkable **from the file**, without recomputing
anything and without trusting that somebody checked it once.

Work components keep distinct names, `delta_work_*` and `total_work_*`, over the same three
groups. **`delta_work_kj_mol` is the sum of every switch since the previous emitted work
observation** — one switch when the work and switching cadences agree, their ratio otherwise. It
is stated in `DECOMPOSITION_SCHEMA["delta_work_meaning"]` rather than left to be inferred.

### `AIS_hs.csv`

The frame-aligned table, holding only rows whose coordinate was saved:

```
path_id, source_frame, observation_index, switch_step, coordinate_frame_index, tau,
total_work_kj_mol, potential_non_scaled_kj_mol, potential_sqrt_scaled_kj_mol,
potential_lin_scaled_kj_mol, potential_reconstructed_kj_mol, potential_direct_kj_mol
```

Every row's work and energy describe one configuration, so a reweighting reads it directly instead
of filtering `AIS_work.csv` — and the failure mode of forgetting to filter is silent.

### Schema v2, and v1 refused

Not a rename. v1's numbers describe a different coordinate, so v1 rows cannot be mixed into a v2
table and a v1 checkpoint cannot be resumed into a v2 run. Both are refused by name, with the
reason.

### Evaluation cost, counted properly

`switching_energy_evaluations` counted basis probes and omitted the two direct evaluations every
switch already performed — understating a path's cost by exactly the part that predates the
decomposition. Replaced by:

```yaml
evaluation_counters:
  basis_probe_energy_evaluations:      # getState inside probes, work and observation alike
  direct_work_energy_evaluations:      # U(tau_j, x_j) and U(tau_{j+1}, x_j), two per switch
  observation_energy_evaluations:      # the direct potential at each frame-aligned row
  total_potential_energy_evaluations:  # their sum
  parameter_updates:                   # counted SEPARATELY: four per probe against three
                                       # evaluations, and the expensive half when solvated
  discarded_energy_evaluations:        # carried across a resume — work thrown away was paid for
  probe_seconds:
```

An "energy evaluation" is one `Context.getState(getEnergy=True)`; a "parameter update" is one
`updateParametersInContext` or `setParameter` push. Both are recorded because on a solvated system
they diverge sharply.

### Verified numerically, not asserted

`tests/test_ais_hs_frame_alignment.py` reopens the real `AIS_trajNNNN.nc`, reads the coordinates of
the exact frame a row names, builds a **fresh** OpenMM Context, and recomputes all three groups and
the direct potential. Sharing no state with the run is the point: a row being consistent with the
runtime's other numbers proves nothing about which coordinate they belong to, which is how v1 was
self-consistent and wrong.

`test_the_potentials_are_not_those_of_the_previous_frame` asserts the old behaviour now **fails** —
recomputing at frame *N−1* must disagree with row *N*. Without it, every other assertion would pass
on a file uniformly shifted by one frame.

Five distinct cadences (switch/2, work/6, frame/10, system/20, checkpoint/15 over 120 steps), so
frame-aligned and unaligned rows both occur; interruption and resume at nine boundaries, checking
for duplicate, missing **and mismatched** rows; implicit and explicit PME.

Measured, at CPU single precision:

| quantity | maximum error |
|---|---|
| implicit, recorded vs independently recomputed | 1.6e-4 kJ/mol |
| implicit, Σ components vs measured work | 2.4e-4 kJ/mol |
| explicit PME, recorded vs recomputed (on 2.1e4 kJ/mol) | 3.0e-1 kJ/mol |
| explicit PME, reconstructed vs direct, in the file | 9.2e-5 kJ/mol |

The frame round-trip tolerance is documented and scaled by the **total** energy, not by each
component: AMBER NetCDF stores coordinates as float32, and a basis value is a combination of three
probe energies each of order the total, with fit coefficients 1, 3 and 4. A bound proportional to a
−9 kJ/mol component inside a −2.1e4 kJ/mol system would fail for reasons unrelated to alignment.
