## 2. Amber H-REMD `rem.log` grammar (§7) — ESTABLISHED BY PARSER TEST

The instruction forbids inferring field meanings. The Amber26 manual PDF is **not** installed, and
the cpptraj parser source (`DataIO_RemLog.cpp`) is **not** shipped — only the compiled object and
the header. What *is* shipped is better: genuine Amber-produced H-REMD logs in the cpptraj test
suite, plus the parser binary itself.

**Environment.** `cpptraj V7.6.2 (AmberTools)` at
`$DATA_ROOT/software/md-stack/conda/ambertools26/bin/cpptraj`, with `sander`, `tleap`,
`cpptraj.MPI` and `cpptraj.cuda` also present.

**Ground truth** — `AmberTools26/test/h_rem/rem.log.save`, a real 4-replica H-REMD log:

```
# Replica Exchange log file
# numexchg is         10
# REMD filenames:
#   remlog= rem.log
#   remtype= rem.type
# Rep#, Neibr#, Temp0, PotE(x_1), PotE(x_2), left_fe, right_fe, Success, Success rate (i,i+1)
# exchange        1
     1     4    300.00    -51.79    -51.79     14.52      0.00    T        0.00
```

**Measured record layout** (79 characters, from column positions in Amber's own output):

```
Rep#     %6d      Neibr#   %6d      Temp0     %10.2f
PotE(x_1) %10.2f  PotE(x_2) %10.2f  left_fe   %10.2f  right_fe %10.2f
Success   %5s     Success rate (i,i+1) %12.2f
```

Header lines: `# numexchg is %10d`, block header `# exchange %9d`, one row per replica per block
with `Rep#` ascending and **1-based**.

**Verified by writing, not just reading.** A 6-state, 5-exchange log generated to this grammar was
parsed by the real cpptraj:

```
Reading 'mine.log' as Amber REM log with name 'M'
        6 Hamiltonian reps.
mine.log, type Hamiltonian, should contain 5 exchanges
```

No errors, no warnings. This satisfies the instruction's requirement that cpptraj compatibility
rest on a real parser test rather than text inspection.

### The `Success rate (i,i+1)` column — a documented open point

Amber's own values could **not** be reproduced from any documented reading of the column:

- exchange 1 reports rates `0.00, 2.00, 0.00, 2.00` — a "rate" of 2.00 is not a fraction;
- the two rows of the *same* pair disagree (exchange 10: `Rep#1 → 0.80`, `Rep#2 → 0.60`;
  exchange 6: `Rep#3 → 0.67`, `Rep#4 → 0.33`).

Rather than invent semantics, its influence on the consumer was measured. Every column was held
fixed except this one, which was replaced by `-999.99` throughout, and both logs were run through
`runanalysis remlog <set> crdidx`:

```
rem.log            : 0 errors
rate_perturbed.log : 0 errors
reconstruction IDENTICAL
```

**Conclusion: the column is not load-bearing for cpptraj's reconstruction.** The implementation may
therefore define an explicit, documented cumulative neighbouring-pair rate and remain
cpptraj-compatible, provided the deviation from Amber's undocumented internal convention is stated.
It must not be presented as bit-compatible with Amber's own value.

`runanalysis remlog <set> crdidx` is also the round-trip test for the future writer: it
reconstructs the coordinate-index history, which must match the known state↔walker mapping.

### A second open point, recorded rather than guessed

Amber's shipped H-REMD logs always pair **every** replica within a block, using a wrap-around
pairing (exchange 1 pairs `1↔4` and `2↔3`; exchange 2 pairs `1↔2` and `3↔4`). This repository's
exchange rule uses alternating adjacent pairs **without** wrap-around, which leaves two replicas
unpaired on alternate attempts. There is no Amber example of an unpaired-replica sentinel. A
self-referencing `Neibr#` parses cleanly in cpptraj, but that is a choice this repository would be
making, not an Amber convention, and it must be documented and tested as such.

## §15 — the generalised-Born contribution scales by `1 - tau`

Supersedes §1 and the decision recorded earlier in this journal. GB is the solute's coupling to a
continuum standing in for solvent, so the whole contribution follows the linear factor. Every term
is multiplied by one global parameter rather than through charges, because GBn2's non-polar term
has no charge dependence and charge scaling would leave it at full strength.

Measured on separate OpenMM force groups, which is what makes this an energy test rather than a
parameter test:

| tau | GB | ordinary nonbonded |
|---|---|---|
| 0.0 | 1.0 | 1.0 |
| 0.25 | 0.75 | 0.5625 |
| 0.5 | **0.5** | **0.25** |

The identity is now `rest2-no-bond-angle-omega/v2` with `generalized_born_scale: "1-tau"`
recorded explicitly. `require_compatible_implementation` refuses to continue a v1 run: a version
bump here says the energy function changed. v1 stays as a historical identity and nothing already
written was rewritten.

## Second pass — the remaining sections, and four defects the tests could not see

### Four defects, and why nothing had caught them

Every existing test of the replica driver either reads its source text or binds one of its methods
to a stub. That caught a great deal. It structurally cannot catch a name that is never bound or an
attribute that is never created, because neither exists until the loop runs — and nothing ran the
loop. Four things had been committed and pushed in that state:

1. **`self.trajectories` was never created.** The frame event called
   `self.trajectories.write_frame(...)` and `close()` called it too, and no code path ever
   assigned it. The per-state trajectories — the entire point of this milestone — were never
   written, and a real REST2 run raised `AttributeError` at its first frame. Committed as done in
   `1614eb5`.
2. **The completion-record builder called `completion_report` without importing it.** Found by
   `ruff --select F821`, not by the suite.
3. **`--rem` never reached the driver.** The flag was parsed, validated, documented and tested at
   the CLI boundary, and `run_grouped` built the driver's `files` namespace without it, so
   `_write_rem_log` returned early every time and no real run ever wrote a REM log.
4. **Three modules were missing from the generated project.** `simple.py` copies the modules a
   generated REST2 directory needs; `rem_log`, `amber_trajectory` and `state_trajectories` were
   never added to that list. A generated directory runs with nothing but its own files on the
   path, so every generated ladder would have raised `ImportError` at launch — invisible to every
   test that imports the templates from the source tree, where all of them are present.

The fix for the class, not just the four: `tests/test_grouped_run_end_to_end.py` runs one complete
grouped REST2 ladder — two states, alanine dipeptide in vacuum, CPU, a few seconds — through the
real `openmm-md` entry point with a real group file, and
`tests/test_generated_project_completeness.py` checks the copy list against the driver's actual
import-time closure computed from the source. Defects 1–3 are each named by a test that fails
without its fix.

### §4 — the resolved state records

`effective_temperature_k = T_physical / (1 - tau)^2`, derived and reporting-only.

Deliberately **not** in `protocol.describe()`, which feeds the scientific identity a continuation

### §8 — the completion report

Neighbouring pairs and an overall figure, and nothing else. One builder,
`replica_statistics.completion_report`, renders both the persisted record and the terminal
summary, so they cannot drift.

Round-trip counting was **removed**, not merely unprinted. It needs a burn-in choice and a window

though the choice had been justified. The committed mapping is preserved in the authoritative
NetCDF, so anyone can compute round trips downstream with their own stated choices. The mapping's
permutation check stayed — that is storage integrity, not analysis.

### §3 — the omega record

The classifier was already right; what it did not do was write down enough to be checked.
`solute.yaml` now records the detection route, the detector version, the ambiguous candidates with
their evidence (bond, both residues by name **and index**, and the sentence the classifier would
have said), and the exact `PeriodicTorsionForce` torsion indices each excluded central bond
protects.

The six cases are in `tests/test_omega_classification_cases.py`, each with the reason it is the
answer it is: ACE-ALA-NME (both omegas protected), X-PRO (eligible — the nitrogen is ring-locked,
so this is not the two-state coordinate the exclusion protects), N-methyl amide (ordinary: an
N-methyl amide isomerises *more* readily than an N-H amide, not less), ligand amide (bond orders
from the SDF, since a SMILES-built solute is one `UNL` residue with no residue evidence),
macrocyclic amide (the ≤ 7-membered ring bound, without which every cyclic peptide's omega would
be wrongly freed for scaling), and an unrecognised modified residue (blocks, with evidence naming
what to declare). A urea is checked too: "a carbon next to one oxygen and one nitrogen" also
describes ureas and carbamates, and those are not peptide bonds.

### §14 — the extension-directory interface

`--extend N` lengthens a run in place, which is right for "this run should have been longer" and
wrong for "here is a second segment, and the first must stay exactly as it was".

`--extend-from PARENT` is the second. The parent is opened read-only; validation, completion
status, identity, Hamiltonian implementation and checkpoint/manifest agreement are all established
before anything local is created, so a refusal leaves no half-built extension directory behind.
The new segment writes its own storage. The parent is never opened for writing on any path.

Two corrections during the work, both worth recording:

* The first version assumed the parent's files were called `exchange.nc` and `checkpoint.nc` —
  what §14's illustration calls them, and what nothing real is called. A generated ladder writes
  `rest2.nc` and `rest2_checkpoint.nc`. Only `restart.json` is assumed now; the analysis and
  checkpoint names are read out of it, because a completion manifest records what it was written
  with. A manifest that does not say is refused rather than guessed at.
* **How the continuation is shown to be genuine.** Not by inspection. The out-of-place extension
  is run beside an in-place `--extend` of the same parent, and the frames must be *identical* —
  the same numbers, not similar ones. A rerun from the input coordinates, a coordinate-only
  restart, or a dropped RNG state each break that immediately. That test passes.

**rem.log numbering across the boundary.** Segment-local, from 1, as Amber does on restart, with
`numexchg` counting that segment's own blocks — which is what cpptraj checks. Both conventions
were measured against the installed cpptraj first: it parses either and does not read the block
number at all, so this is a deliberate choice rather than a constraint, and the absolute position
is recorded as `first_exchange_number` in the extension provenance.

### The staging exception (§16.4 against an existing invariant)

§16.4 requires the validation dataset to be generated in `MD-project/data/ALA/`. The generator
refuses any output inside a git working tree, on the stated grounds that an ignore rule is not
protection because it is one `git add -f` from being wrong. That reasoning is sound and the rule
stayed.

Rather than dropping it or working around it, the exception was made **checkable**: an opt-in
variable (`MD_TEMPLATES_ALLOW_STAGING=1`), a marker file `.md-staging` visible in the tree, and
`git check-ignore`'s own opinion that what is created *beneath* the root is ignored — asked about a
system directory, not about the root, which is usually tracked and holds a README. Any one missing
and the refusal stands, and the refusal now says exactly what would make it pass.

### §11 — the pin, and what it costs

`components.yaml` / `components.lock.yaml` request and record
`feat/rest2-state-trajectories` at `60213195e4a1d13e5d83592f94cdc23bcc8c59f2`, and every example
system configuration was repinned. The journals and the instruction document keep the old SHA:
they record what was true when they were written.

**A real consequence, recorded plainly.** The storage schema moved from v2 to v3 and v2 is
*refused*, not migrated. v3 keeps coordinates in per-state Amber trajectories rather than inside
the exchange record, so a v2 file is a different file and not a shorter one; a migration would
mean fabricating per-state trajectories that were never written. **REST2 and rREST2 datasets
written under v2 can no longer be resumed or extended.** They remain readable as finished results.
`tests/test_v2_append_capability.py` previously asserted the opposite; it was not patched to keep
passing but rewritten to assert what is true, including that the refusal names the schema it found
so a reader knows which dataset it concerns and that the file is untouched.

### The box, since it is easy to misread

`padding_nm: 1.5`, dodecahedron, 1.0 nm cutoff, TIP3P, 0.15 M NaCl, 1790 particles. OpenMM
padding semantics give a width of 2×0.473 + 1.5 = 2.45 nm, whose dodecahedral perpendicular height
(1.73 nm) is below the 2.0 nm a 1.0 nm cutoff requires — so the `grow` policy enlarged the box to
**3.0 nm**. The resulting solute-to-nearest-periodic-copy separation is **2.05 nm of water**, and
the maximum legal cutoff is 1.061 nm against the 1.000 nm used. The effective padding is therefore
larger than requested, driven by the cutoff constraint rather than by the padding request.

### A stated deviation from the §16.4 layout

§16.4 names `common/` for the shared inputs. The `md-openmm setup` route calls that directory
`input/`, and `paths.sh` and every generated launcher address it by that name. It holds exactly
what §16.4 means by `common/`: the topology, the serialised System, the initial state, the solute
record, the force-field record and their checksums. It was left as `input/` because renaming it
would break the generated tree for a cosmetic match, and the registration tooling addresses the
dataset by content rather than by that name.

### Registration — carried out, after two defects were corrected

The first registration wrote the dataset to
`$MD_DATA/projects/2026-08/ala-nvt-rest2`. That was wrong, and the question that found it was
simply "why is it under `projects/` rather than a project namespace".

**The path was invented.** The installed MD-data contract puts every dataset at

```
$MD_DATA/{namespace}/{yyyy-mm}/{dataset_name}/
```

stated in `md_data_contract.py`, in `dataset-v1.schema.json`, and followed by every dataset already
under `$MD_DATA` (`MD-project-dev-test/2026-08/ALA-explicit`, `krrest2/2026-08/ALA-implicit`,
`md-project-examples/2026-08/ALA-explicit-tutorial`). `md-data-register` invented a fourth level
above it — an ownership bucket, `common/` or `projects/` — and put the date in the namespace field.

Wrong twice over: the contract has no such level, and **a bucket is not a namespace**. Every
project-owned dataset ever registered would have landed in `projects/`, which is precisely what a
namespace exists to prevent. The result had three segments with a month in the middle, so it slipped
past a shape check while being meaningless.

**No `dataset.yaml` was written at all.** The contract's own manifest — the one MD-data's tooling
reads — was never emitted; only `dataset.resolved.yaml`, a format this project invented. A
registered dataset without it is undiscoverable however complete its bytes are.

Both survived because every check was against this project's *reading* of the contract. The suite
now validates the emitted manifest against the schema **shipped with MD-data**, discovered through
the machine configuration rather than hardcoded, and skips loudly rather than passing when that
schema is not installed.

Three smaller things the correction uncovered:

* `verify_staged` reported the manifests the tool itself writes as strays, so a registration
  resumed after the commit stage refused its own output — the one case the transaction exists to
  survive.
* A directory the draft said nothing about was silently dropped from `components`, leaving the
  manifest describing a dataset with fewer parts than it has.
* `origin.commit` was never resolved. A tracked configuration cannot contain the SHA of the commit
  that adds it, so it is read from the project checkout at registration — and a dirty tree is
  refused rather than recorded, because that SHA would name a tree that exists nowhere.

The corrected registration:

```bash
./bin/md-data-finish --idata ./data/ALA/
./bin/md-data-register --idata ./data/ALA/ --iconfig ./configs/data/ALA.yaml
```

```
# destination           : $DATA_ROOT/DATA/MD-project-dev12-test/2026-08/ALA-REST2-explicit-5ns
# files                 : 113
# same filesystem       : False
# contract manifest     : .../dataset.yaml
# committed manifest    : .../dataset.resolved.yaml
# .../MD-projects/data/ALA -> ../../../DATA/MD-project-dev12-test/2026-08/ALA-REST2-explicit-5ns
# REGISTERED
```

A **cross-filesystem** move: stage, verify every checksum at the destination, commit, remove the
source, symlink, verify. Afterwards `sha256sum -c SHA256SUMS` at the destination reports **112 of
112 OK, no failures**, and the emitted `dataset.yaml` **validates against the installed
`dataset-v1.schema.json`**:

```

namespace    : MD-project-dev12-test
dataset_name : ALA-REST2-explicit-5ns
role         : project        status: complete
origin       : b753fff8f9fc @ https://github.com/csy0000/MD-project
templates    : 60213195e4a1
components   : REST2, REST2_ext1, bin, eq, input, min
```

**The canonical path is** `$DATA_ROOT/DATA/MD-project-dev12-test/2026-08/ALA-REST2-explicit-5ns/`,
which is `$MD_DATA/{namespace}/{yyyy-mm}/{dataset_name}` — the shape the installed contract
requires, so §13's suggested `validation/2026-08/alanine-dipeptide-nvt-rest2/` was not used, exactly
as §13 allows where the contract requires otherwise. There is no numbered root and no name encoding

recorded above; that absolute path appears only in the ignored `config/machine/machine.config` and
